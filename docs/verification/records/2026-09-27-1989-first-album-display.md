# 1989 Deluxe 初回アルバム表示の名称遅延調査

**最終状態：修正・検証・配布APK作成済み。** 同じ検証前DBから通常検索を行い、1989 Deluxe全19曲の英語公開を約15.6秒で確認した。修正前は120秒後も16/19だった。初回の通信・言語判定時間は残る。以下の前半は修正前の調査記録で、末尾に最終ソースでの結果と検証制約を記載する。

## 課題と範囲

- ユーザー報告：初めて検索した Taylor Swift「1989 deluxe」のアルバムを開いても、名前解決された名称が画面に出るまで時間がかかる。前回の対策後も解消していない。
- 期待：初回のアルバム表示で、取得・判定済みの名称を速やかに表示できること。
- 対象ソース：`bf9c0e85`（`outertune: stabilize metadata names and prioritize album resolution`）。依頼に従って既存の変更を先にコミット済み。
- 初回依頼は調査のみ。その後、ユーザーから関連する穴を洗い出したうえでの修正依頼を受け、下記の実装・検証へ進む。
- 確認点：実際の検索→アルバム遷移で取得、英語判定、公開DB、画面表示の待ちを区別する。版の違いを避けるため、実応答のアルバムIDを記録する。

## 着手時の根拠・仮説

- 前回の Evolve 約10秒は、独立したメモリDBと専用observerでの名称取得・判定の測定。実際のホーム・検索候補処理、表示用singleton、Compose画面の反映時刻は含まない。
- コード確認：表示用名称は Compose の `mutableStateOf` で、アルバム・曲のラベルが現在値を直接参照している。古い名称を固定する `remember` は見つかっていない。
- コード確認：判定の再実行対象は限定されたが、公開準備・DB確定は全体の入力を照合する。無関係な候補の変更でも、既に判定済みの名称の公開を延期し得る。既存の `unrelatedAlbumArrivingDuringClassification` デバイステストもこの挙動を要求している。
- 仮説：この公開待ち、複数段階の原題取得、検索候補・アーティスト情報取得との競合が実症状に寄与している。実測前に主因とは断定しない。

## 確認した残存問題

### 1. 無関係なデータも待つ一括公開

`MetadataNameRepository.kt:274` 以降は再判定を対象別に絞ったが、`OriginalNamePublication.kt:28` は未判定の原題がDB全体に一つでもあれば公開準備を延期する。さらに `MetadataNameRepository.kt:307–329` は処理中に別の `en/und` 名称・参照が変わっても公開を見送る。

これは既存 `OriginalAssessmentRetentionDeviceTest.kt` の `unrelatedAlbumArrivingDuringClassification` でも要求している挙動。無関係なアルバムAの判定を保存しても、Bの判定が終わるまでAの公開を待つ。前回の対策は判定の再実行を減らしたが、この公開単位は残した。

予備走行では `SAXnfvceZc4`（This Love）の原題を05:40:09 UTCに取得し、05:40:31のDBでENGLISH判定が保存済みなのに公開行がなく、05:41:01のDBでは英語公開を確認した。予備走行はDeluxeの画像内再生ボタンを押してキューを取得した経路なので、初回画面遷移の所要時間には使わない。判定済みと未公開が同時に存在した証拠としてのみ扱う。

### 2. 欠けたアーティスト欄が、確認済みの曲原題まで止める

`saveOriginalTitle`（`MetadataNameRepository.kt:1022–1037`）では、以前の原題証拠にARTIST行がある一方、新しいMusic応答のアーティスト欄が空だと `completeArtistIdentities=false` になる。続く `completeSnapshot` がfalseとなり、SONGを含む今回の候補すべてを空にする。

一方、同じ動画IDの英語アルバム行とMain配信元説明から、曲原題・そのアルバムへの収録を確認できる場合がある。アーティスト情報の欠落を理由に、この独立した曲の証拠まで拒否するため、先に通常曲取得がARTIST証拠を保存したかどうかで結果が変わる。

実応答の追加確認はPCから匿名・英語/JP、製品と同じクライアント定義で実施。`iIuOsKBiNPY`、`r2TY67fxu9M` などで、アルバム行の同ID・ATV・空のアーティスト欄と、Mainの構造化された配信元説明を確認した。説明形式自体を原因とした当初の仮説は採用しない。PCの追加応答はエミュレータの当該通信そのものを記録したものではないが、DBの「原題保持、アルバム文脈なし、再取得EMPTY」とコードの分岐に整合する。

同じ検証前DBからの予備走行では最終13/19、通常UI走行では16/19と結果が異なり、予備走行で未解決だった All You Had To Do Was Stay / Bad Blood / Clean は通常UI走行で英語になった。取得順依存を無視して固定の遅延時間として扱えない。

### 3. 再生制限3曲の不足で、別ID対応を全件破棄する

同じ正規プレイリスト `OLAK5uy_mtnHS42OzbtQ7iSxEDnTcbrwfEAW85ano` について、追加取得したbrowseは19件、nextは16件だった。nextは `isInfinite=false` で、続きのキューtokenもない。欠ける3件はVoice Memoの `cV73DqEtqs8` / `16kF9RwwcM4` / `4tegR9aUobo`。

`PlaylistSongReferenceParser.kt:109–111` は両応答の安定項目ID集合の完全一致を要求し、不一致なら例外を投げて対応結果を一件も返さない。そのため、同じプレイリスト・同じ安定項目IDで確認できた次の対応も利用されない。

| 曲 | playlistSetVideoId | 音源側ID → 表示側ID |
| --- | --- | --- |
| Wonderland | `A5B03A001F101332` | `YXspld9F7-A` → `JhICcmiIE80` |
| New Romantics | `67000BB798216A47` | `KsPK-waqvf0` → `wyK7YuwUWsU` |

アプリDBでもプレイリスト参照取得はFAILEDになり、この2曲の有効な参照はない。単に長く待てば必ず解決する状態ではない。対応IDは名前や曲順から推定していない。

### 実装内容

- 独立した曲・アルバムの証拠を保存し、欠落した人物欄は同じsource・同じ原題・現在の完全なMain creditで確認できる既存IDに限って保持する。変更された原題と不完全な関連情報は混ぜない。
- アルバムが先に成功した後の完全な曲詳細、アルバムMainの実行中に届く詳細、補完Mainの実行中に届く別の詳細を扱う。追加照合は不足する証拠と入力の意味が変わった場合だけで、同じ入力の観測ごとにMainを繰り返さない。失敗後の通常経路へ5分の待機を共有する。
- 正常終了したbrowse/nextにおいて、GREY_OUTかつ再生endpointのない欠落項目を明示して、確認できた対応を返す。不明な欠落、重複、playlist ID・endpoint矛盾、continuation失敗は拒否する。
- 既存の対応は最新観測を用い、同じ制限項目や一時的な原情報欠落では保持、確認された再割当・削除では撤回する。
- 公開の依存範囲を対象候補・現在の参照元・関連アルバムの曲原題に限定。無関係な判定失敗・未完了出力は完成済みの名前を妨げない。同じ人物の別作品追加による不要なモデル再実行も抑える。
- 背景の独立した判定は最大8グループ分をまとめて公開準備し、全DBの走査・証拠JSON生成の回数を減らす。各判定の例外は独立させ、前景を優先する。
