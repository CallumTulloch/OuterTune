# アーティスト画像の保存

## 課題と範囲

- ユーザー報告：ライブラリのアーティスト一覧で画像が出ない。
- 後の補足：再起動で反映されたため、保存自体の失敗というより同期・表示反映の遅れだった。今回の修正は画面購読や再起動に依存する補完開始と更新漏れを対象にする。
- 期待：オンライン人物IDが判明している保存済み人物について画像を補完し、取得したURLをDBへ残す。空応答・通信失敗で保存済み画像を消さない。名前・ブックマーク・曲との関係を保持する。
- 言語対応の現行未コミット差分を正とし、両課題の同時修正はユーザーが明示認可した。
- 画像ファイルの永久保存は範囲外。画面で取得した画像は既存Coilディスクキャッシュを利用する。キャッシュ設定が有効で画像が残っていれば再起動・オフラインでも再表示できる通常経路を確認する。
- Gradle・端末操作は親エージェントのみ。対象ソースは作業中のHEADと未コミット差分。

## 原因としてコードで確認した内容

1. `ArtistViewModel.fetchArtistsFromYTM` は人物ページを取得しても画面stateへの保存だけで、プロフィール画像をDBへ書かない。
2. 画像補完はLibrary/Stats画面のViewModel内にあり、画面の生成・購読に依存する。曲保存後の人物画像補完を常駐処理で保証していない。
3. `SyncUtils.syncRemoteArtists` は既存人物行の画像欠損を更新せず、新規行だけに画像を保存する。
4. 既存の画像更新は取得開始前のArtistEntity全体copyを上書きするため、取得中に変更した名前・ブックマークを戻し得る。またnull画像で保存済み画像を消し得る。
5. 名称候補Repositoryも人物詳細を取得するが、名称の取得TTLと画像の保存状態は別問題。未登録時に名称だけ取得した後、人物を保存すると、画像欠損を名称キャッシュのTTLで補完できない場合がある。

## 改修方針

- 既存のオンライン人物IDに対するプロフィール部分更新をDAOへ集約する。空画像は既存維持、未知ID・ローカル人物の画像を書き換えない。
- 保存済み人物を監視する`ArtistImageRepository`をAppで起動する。名前のTTLから独立し、同じ人物の要求を共有して最大2要求で補完する。
- 成功画像は10日、画像なしは1日、失敗は5分を目安に再試行する。再起動時も失敗・空応答の待機を引き継ぐ。
- 人物ページ・同期・既存の画像取得経路を部分更新へ接続し、Library/Statsの独立した取得ループを集約する。
- DBの既存画像URL欄を利用するためschema変更はない。

## 合格条件

- 画像のない保存済み人物が、ライブラリ画面固有の更新操作なしで補完される。
- 同じオンライン人物に対応する内部IDを維持し、名前・ブックマーク・曲との関係が変わらない。
- 通信失敗、画像なし、違う人物IDの応答で保存済み画像が壊れない。
- 名称キャッシュが先に作られた場合も、後から保存した人物の画像が補完される。
- DB再オープンで画像URLが維持され、取得済みキャッシュで一覧画像が再表示される。

## 実装した内容

- `ArtistsDao.saveArtistProfile(ArtistItem)` を追加。オンラインIDが一致する既存の非ローカル人物だけ、画像URL・channelIdを部分更新する。画像がない場合は既存画像と画像更新時刻を維持する。名前・ブックマーク・人物関係は更新しない。
- App起動時の `ArtistImageRepository` が保存済み人物を監視する。欠損・10日経過の画像を最大2要求で補完し、同一人物の要求を共有。名前キャッシュの成功期限には依存しない。空応答1日/通信失敗5分の待機を専用preferencesへ保存し、成功の期限は画像を保存したDB行自身で管理する。
- HTTP前とDB保存直前で国・認証条件を確認し、途中で条件が変わった応答は保存せず新条件で取り直す。返った人物IDが違う場合も保存しない。
- 人物ページ・ホームの既存人物取得・同期・人物登録時にプロフィール部分更新を使用する。Library/Statsの画面固有の画像取得ループを削除した。
- 画像バイトの保存方式とUIキャッシュ設定は変更していない。

## 追加症状：ダウンロード済みアルバムの人物名

- ユーザー報告：曲をダウンロードした後、ライブラリのアルバム行へ人物名が表示されるには、対象アルバムを一度開く必要がある。
- コードで確認した原因：`DownloadUtil.prepareAndDownload` は曲のalbum ID/titleを補って `DatabaseDao.insert(MediaMetadata)` へ渡す。この経路はアルバムの仮行と曲との関係を作るが、オンライン曲の人物をアルバム全体の人物へは昇格しない。`ArtistCreditRepository` のアルバム補完も同じ参照情報が対象。一方、アルバム画面の `AlbumViewModel` は正規AlbumPageヘッダーを保存するため、この時点で初めて `album_artist_map` とアルバム自身のcreditが揃う。
- 表示は `Album.artistDisplayText()` が参照するDBのcredit/人物関係に従っている。画面を開くまで不足していたヘッダーを保存後に自動取得することで修正する。

### アルバムについて実装した内容

- App起動時の `AlbumMetadataRepository` が保存済み非ローカルアルバムの不完全creditを監視する。保存・同期・再生・ダウンロードのどの入口で作られた行も対象にし、未保存の検索結果をライブラリへ追加しない。
- 現在のコンテンツ言語・国・認証条件を固定した `YouTube.album(withSongs = false)` から正規ヘッダーを取得する。曲の人物からアルバム全体の人物を推定しない。
- `AlbumsDao.applySavedAlbumHeader` は一致する保存済みアルバムにcreditと人物関係だけを反映する。AlbumPage全体のupsertを使用しないため、タイトル・曲数・duration・ブックマーク・既存の曲関係を維持する。空応答・失敗で既存creditを消さない。
- 別言語のRAW/PARTIAL creditは、正規ヘッダーがCOMPLETEで、過去に確定した人物IDを全て明示的に含む場合だけ補完できる。名前の一致だけで同一人物にしない。既存のCOMPLETE/CONFLICTを別言語で置き換えない。
- 失敗5分・空または不完全な応答1日の待機を、既存 `metadata_fetch` の `album-credit:` コンテキストへ保存する。名称キャッシュの成功期限と独立し、再起動後も待機を維持する。成功後の完全性はアルバム行そのものを確認し、後から欠損したcreditを古い成功期限で止めない。
- `acceptHeader(AlbumItem, requestLocale, requestContextKey)` を名称取得との共有入口として公開した。要求前後とDB更新直前に言語・国・認証条件を確認し、古い応答を保存しない。同時補完は最大2件に制限し、同じ条件のアルバム要求を共有する。
- 既存の列・テーブルを使用し、schema変更はない。
