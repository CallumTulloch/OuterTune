## 1. フォルダナビの端末内検索

### 現象とコード上の根拠

- 検索結果を押しても対象曲が再生されず、再生アニメーションも付かない。
  `FolderScreen` は検索時に `filteredSongs` を表示するが、`onPlay` は常に
  `mutableSongs`（現在フォルダ直下の曲）をキューへ渡し、この一覧から開始位置も探している。
  検索は `searchSongsAllLocalInDir` により配下のサブフォルダも対象とするため、一覧が一致しない。
  直下に曲がなければ空キューになり、対象曲が直下になければ開始位置は -1 になる。
  `MusicService` は空一覧では新しいキューを設定せず、負の開始位置は0として扱う。
- 曲行には既に現在曲IDと `isPlaying` が渡されている。アニメーションがない現象は、
  選択曲が再生対象にならないことから説明できる。独立した描画不具合の有無は端末未確認。
- 検索欄には `ImeAction.Search` があるが、`KeyboardActions` と物理Enterの処理がない。
  共通検索の `SearchBarInputField` は両方を `onSearch` に接続し、物理EnterはKeyUpで一度だけ確定する。
  `SearchScreen` は確定時にフォーカスとキーボードを閉じ、結果画面を維持している。
- 検索開始でアイコン等の行がMaterialの `TextField` を含む行へ切り替わる。
  行の高さ・入力欄の内側余白が揃っていないことがレイアウト変動の主な候補。
  フォーカス時のスクロール補正等も含め、実際のずれ方は未確認。
- 付随して、空文字では `filteredSongs` を消さず、毎回独立した非同期検索を開始している。
  UI側の `collectLatest` ではViewModel内で開始した検索を取り消せず、古い応答が新しい結果を上書きし得る。
  検索時も複数選択・全選択は直下一覧を参照し、ソート条件は検索結果に適用されていない。

### 提案

1. 表示対象の曲一覧を一つに定め、描画・再生キュー・IDによる開始位置・選択操作をそこへ揃える。
   検索中は検索結果の表示順で選択曲から再生する。既存の曲行と再生状態表示を利用する。
2. フォルダ配下限定という検索範囲を維持し、現行ローカル検索の入力・確定・結果管理を参考にする。
   アルバム等も含む全ライブラリ検索への置換は今回の案に含めない。
3. 共通検索から入力部品を必要な範囲で切り出し、IMEと物理Enterを同じ確定処理へ接続する。
   入力中の検索は維持し、Enterでは最新語の検索を確定してキーボードを閉じ、結果を残す。
   入力前後の行高・余白を揃え、検索モードとフォーカス状態を別に扱う。
4. 最新の入力だけが結果を更新できるようにし、空文字で結果を消す。
   共通ローカル検索の `flatMapLatest` 型の管理を参考に、検索語と結果の対応を保つ。
   クリア・終了・再開・戻るの状態処理も統一する。
5. 検索結果の並び・件数・全選択を表示内容と整合させる。

## 2. 曲ナビの三点メニュー

- `LibrarySongsScreen` の上部チップとメニューは、同じ `onFilterSelected` と保存状態を使っている。

## 3. ライブラリ内の三点メニュー

### 現象とコード上の根拠

- 上部は `LibraryScreen` のカテゴリ別 `Library*ContentFilterMaskKey` を更新する。
  アルバム・アーティスト・プレイリストの三点メニューは旧 `AlbumFilterKey` 等を更新している。
  埋め込み表示の取得処理は親から渡された出所条件を使うため、メニューで変更した旧条件は使われない。
  「いいね済み」も旧条件だけを書き換えるため、メニュー項目の削減だけでは直らない。
- `Dropdown` の展開行は通常の `DropdownMenuItem` と別実装。
  「<」と文字を置く内側のRowに中央揃え指定がなく、行レイアウトが揃っていない。
- アルバム・アーティストの現行「いいね済み」は、その項目自身の `bookmarkedAt` で判定する。
  いいねした曲の収録先という意味へ変えない。プレイリストには現状この項目がない。
- 同じ画面部品は独立したアルバム・アーティスト・プレイリストナビでも利用されている。
  独立ナビには上部に旧条件のチップがあるため、埋め込み表示との呼び出し条件を区別する。

### 提案

1. ライブラリ内では出所条件を上部に集約する。
2. アルバム・アーティストのメニューには、今後の拡張性のために
   「< 絞り込み」の展開階層（現行の「ライブラリを絞り込み」）を残す。
   配下にはチェック表示付き「いいね済みのみ」を置き、再度押すと解除する。
   重複する出所項目を配下から削除し、展開行の文字列と「<」の縦位置・余白を揃える。
3. 親の出所条件と独立したいいね条件を、実際の一覧取得に渡す。
   出所を複数選んだ場合は既存のORを維持し、その結果にいいね条件をANDで適用する案。
   出所未選択でいいねのみを有効にした場合は、従来のいいね一覧に合わせ、曲を未取得の
   ブックマーク済みアルバム・アーティストも扱えるようにする。
   親が既に空選択を「全出所」に変換する箇所で、未選択という情報を失わないようにする。
4. カテゴリごとに選択状態を一つだけ持ち、出所変更でいいね条件が消えたり、
   非表示の旧設定が別ナビへ影響したりしないようにする。
   独立ナビは上部で操作できるため、重複メニューを残す必要はない。
5. プレイリストの重複絞り込みを削除し、作成・インポートを残す。
   既存DBのブックマーク情報を利用するため、本案ではDBスキーマ変更は不要。

## 実装時の合格条件と順番

- まずフォルダ検索を修正する。直下に曲がなくサブフォルダだけに曲がある場合でも、検索結果の
  選択曲から再生できる。再生・一時停止表示が実際の状態と一致し、IME／物理Enterが一度だけ確定する。
- 検索欄の開閉・再フォーカス・キーボード表示でヘッダが意図せず動かない。
  連続入力・クリア・再検索で古い結果が復活せず、検索結果のソート・件数・全選択が一致する。
- 次に曲ナビの重複項目を削除し、上部の絞り込みと他のメニュー操作を確認する。
- 最後にライブラリのメニューと実際の条件を整理する。
  「< 絞り込み」の展開階層が残り、文字列とアイコンの位置が揃い、
  配下の「いいね済みのみ」のチェック表示と実際の絞り込みが一致することを確認する。
  出所×いいねの組合せ、解除、0件からの解除、カテゴリ切替・再起動、独立ナビへの影響を確認する。
- ロジックは近傍の検索／絞り込みテスト、見た目と再生は対象画面で確認する。
  メニュー削除や余白変更のためだけの単体テストは増やさない。

方針相談時の確認は静的なソース読取のみ。以下に実装後の確認を記録する。

## 実装内容

- フォルダ検索は入力直後に前のDB監視をキャンセルし、300msの入力待ち後に最新語を検索する。
  Enter確定は入力待ちを省略する。検索語と結果を一緒に保持し、空文字・空白だけの入力で結果を消す。
  同じ文字列のカーソル操作では検索を再起動しない。
- 通常表示・検索表示とも `visibleSongs` を描画・再生・全選択・選択曲の解決に使う。
  ソートは共通処理にし、開始位置は曲IDで求める。存在しないIDから別の曲を再生しない。
  検索中の件数は検索結果数。再生インジケーターは既存の曲行を利用した。
- 共通検索の入力部品をフォルダ内でも使用。行高は検索前後とも48dp。
  IMEと物理Enterで確定し、結果を維持してフォーカス・キーボードを閉じる。
  検索終了と検索語クリアを用意し、スクロールによるヘッダの再表示だけではフォーカスを取り直さない。
- 曲ナビとプレイリストの三点メニューから重複する出所選択を削除した。
- ライブラリ内のアルバム・アーティストは共通の「< ライブラリを絞り込み」メニューを使い、
  配下にチェック付き「いいね済みのみ」を表示する。展開行はアイコンと文字を中央揃えにした。
  通常項目にチェック状態を渡せるようにし、選択時は親メニューも閉じる。
- いいね条件は親のライブラリ画面でカテゴリごとに保存し、出所条件と共にViewModel・DAOへ渡す。
  明示した出所はORで結合し、ブックマーク条件をANDで適用する。
  出所未選択なら曲未取得のブックマークも含める。解除すると元の出所一覧へ戻る。
  独立ナビの旧設定を書き換えない。DBスキーマの変更なし。

  一時停止後500msでの画像一致が失敗した。保存画像では停止アイコンを確認できる。

  最大4秒で確認するようテストを修正した。製品の再生表示は変更していない。
  テストホストのステータスバー余白も追加し、スクリーンショットは描画を待って取得する。
  ログ：`build/navigation-device-tests.log`、14.091秒。
