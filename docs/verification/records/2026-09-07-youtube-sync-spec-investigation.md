# YouTube再生・同期仕様と次の改善方針

## 対象と確認範囲

- ユーザー依頼：直近コミット後も発生する年齢制限エラー、同期後のいいね・YouTubeへの反映・同期解除後の残存／削除、検索条件と今後の改善方針を確認する。
- 対象ソース：`7bc8bfa5847652d9cd6e7883de562574be36147e`、ブランチ `restart/artist-20260905`。着手時の未コミット差分なし。
- 追加情報：対象曲はアプリでアルバムからダウンロードしたものを使う。別の同名検索結果に置き換えない。
- 今回は調査と仕様整理。製品コード・DB・設定・APKを変更せず、Gradleを実行しない。提供された認証情報を本記録・調査ファイルへ保存しない。
- 合格条件：登録状態と外部反映をコードの実際の条件で説明する。再生について、確認済みの公式サイト動作と未確認の端末状態を区別し、次に必要な検証を特定する。

### 「ダウンロードした曲」を確認する際の重要点

- 通常のアルバムダウンロードはMedia3の内部キャッシュを使う。外部フォルダへ移す仕組みは別経路。
- `DownloadUtil.kt:276–278`は先に曲情報をDB登録する。その後`:288–304`で再生URLを取得し、成功して初めてダウンロード要求を作る。
- 再生URL取得が年齢確認などで失敗すると`:305–308`でログを出すが、登録済みの曲情報は残る。準備段階の失敗をダウンロード失敗として画面へ十分伝えていない。
- 内部キャッシュに必要な音声があれば、`MusicService.kt:740–746`は再生URL取得より先にキャッシュを使う。実体がない場合は`:755–763`からオンライン取得へ戻る。ダウンロード登録／完了インデックスだけで、音声の実在は保証できない。
- 外部保存の場合、`:718`のキュー内localPath判定とメモリ上のファイル索引に依存する。古いキュー情報や索引読込前の再生では実体があっても見逃す可能性がある。今回ユーザーが外部移動を行った証拠はない。
- 曲の長さを補う`recoverSong`の通信失敗は別のコルーチン内で扱うため、それ自体が音声再生の年齢制限エラーになる経路ではない。

次の検証：ユーザーの保存済み曲のID・アルバムID、`dateDownload`、内部ダウンロード状態とキャッシュ量、必要なら外部ファイルの実在を確認する。同じ曲を再生し、キャッシュ／オンラインのどの分岐へ進むか、各通信方式のstatus・HTTP／解析／URL検証エラーを秘密値なしで記録する。公式で再生できたこととOuterTuneでの解決を別に判定する。

## 2. 同期と保存状態の現行仕様

DB登録、いいね、ライブラリ所属、音声ダウンロード、プレイリスト所属はそれぞれ別の状態。複数が同じ曲に重なる。

| 同期の取得対象 | 新規登録時の状態 |
| --- | --- |
| いいねした曲 | `liked=true`。この処理だけではライブラリ所属は付けない。 |
| 曲／アップロード曲 | ライブラリ所属を付ける。新規なら`liked=false`。既存のいいねは維持する。 |
| プレイリスト内の曲 | 曲情報とプレイリスト所属を登録。新規ならいいね・ライブラリ所属なし。 |
| アルバム／アーティスト | 対象の情報を登録する。同期処理そのものが全収録曲を登録するわけではない。 |

根拠：`app/src/main/java/com/dd3boh/outertune/utils/SyncUtils.kt:283,301,340,362,428,504,628`、`app/src/main/java/com/dd3boh/outertune/db/entities/SongEntity.kt:29–78`。登録済み曲一覧はライブラリ所属・いいね・ダウンロードのいずれかで表示する（`db/daos/SongsDao.kt:104`）。

### アプリ操作がYouTubeへ反映されるか

| 操作 | 現行コードの挙動 |
| --- | --- |
| 曲のいいね／解除 | YouTubeへの送信あり。自動同期OFF／読み取りのみでも送信を止めない。 |
| 曲のライブラリ追加／解除 | YouTube側の曲単位ライブラリ所属を変える処理は未実装。アプリ内の変更。 |
| 同期対象プレイリストの名前変更・曲追加／削除・並べ替え | YouTubeへの送信処理あり。ただし編集権限・browseId・曲所属ID・操作入口で実行条件が異なる。 |
| 同期対象プレイリストそのものの削除 | YouTubeへの削除要求あり。「アプリからだけ外す」とは限らない。 |
| アプリ内だけのプレイリスト | 通常はアプリ内の更新。作成時に「同期する」を選ぶ場合はYouTubeにも作る。 |
| 自動同期OFF | 自動取得を停止する。送信全体の停止や取込済みデータの削除はしない。 |
| ログアウト | 保存Cookieとアカウント情報を消す。曲DBは消さない。 |

根拠：`SyncUtils.kt:138,193,240,250`、`SongEntity.kt:61`、`ui/dialog/CreatePlaylistDialog.kt:60`、`ui/dialog/AddToPlaylistDialog.kt:94,197`、`ui/menu/SongMenu.kt:311,326`、`ui/menu/PlaylistMenu.kt:328,405`、`ui/screens/playlist/LocalPlaylistScreen.kt:405,557`、`App.kt:224`（app配下のパスは`app/src/main/java/com/dd3boh/outertune/`相対）。

送信処理があることと、反映成功を保証できることは別。多くはDBを先に更新し、APIのResult失敗を処理していない。永続的な送信待ち・再試行キューは確認できない。

### 同期を解除しても曲が残る理由と現在の削除操作

- 自動同期OFFとログアウトは登録済みDBを削除しない。既定の競合解決も「追加のみ」であり、YouTubeから消えたものをアプリから消す設定ではない。
- 一覧から外すには、残っている状態に応じて「ライブラリから削除」「いいね解除」「ダウンロード削除」が必要。ハートによる解除はYouTubeへの送信を伴う。プレイリスト所属や再生履歴は別に残る。
- 「ライブラリから削除」は入口によっても違う。SongMenu／PlayerMenuはライブラリ所属といいねを解除する一方、YouTubeSongMenuはライブラリ所属だけを解除する（`ui/menu/SongMenu.kt:208`、`PlayerMenu.kt:433`、`YouTubeSongMenu.kt:157`）。
- 曲のDB行を完全削除するDAOはあるが、オンライン曲を個別／一括で完全削除する通常画面は確認できない（`db/daos/SongsDao.kt:579`）。プレイリスト削除でも曲DB行は残る。
- 一括いいね解除は選択メニュー、全ダウンロード削除はストレージ設定にある。一括ライブラリ解除は同じ選択メニューにない（`ui/menu/SelectionSongsMenu.kt:206`、`ui/screens/settings/fragments/StorageFrag.kt:472`）。
- 曲に「どのアカウントから同期したか」「同期／手動追加のどちらか」を記録していない。現行DBのまま「同期で増えた曲だけ一括削除」を正確に行うことはできない。
- 再同期すると、YouTubeに残っている曲が再度取り込まれる場合がある。ローカル除外を維持する仕組みも必要。

### 正常な仕様として扱うべきでない不整合

1. **読み取りのみの制御漏れ**：いいね、プレイリスト名変更、プレイリスト削除などを送信する。設定確認を共通の送信処理に集約する必要がある。
2. **失敗しても成功表示**：`ui/screens/settings/fragments/SyncFrag.kt:118–123`、`ui/screens/playlist/LocalPlaylistScreen.kt:767–770`は同期結果のBooleanを無視する。
3. **二重送信**：SongEntityのいいね送信に加えてメニューやプレイヤーがSyncUtilsから同じ変更を送る。曲追加も入口のonPreAddと共通ダイアログで重複する。
4. **重複確認より先に外部更新**：`ui/dialog/AddToPlaylistDialog.kt:184–200`は重複確認前にonPreAddを呼ぶ。入口によって、後の確認でキャンセルしてもYouTubeへ追加済みになり得る。
5. **追加直後の所属ID不足**：曲追加の応答を保存しないためsetVideoIdがなく、再取得まで削除／並べ替えが外部に反映されない可能性がある（`db/daos/PlaylistsDao.kt:203`）。
6. **プレイリスト全体追加のID誤用**：`ui/menu/YouTubePlaylistMenu.kt:318,327`、`PlaylistMenu.kt:442,445`に端末内IDをYouTube向け追加元IDとして使う経路がある。

以上はコード上の条件／欠陥を確認したもので、開発用アカウントのいいねやプレイリストを実際に変更して検証した結果ではない。

## 3. 検索条件と改善順序の提案

現状の検索はオンライン／アプリ内の対象切替と、曲・動画・アルバム・アーティスト・プレイリスト等の種別切替が中心。ライブラリの曲一覧には別途「いいね」と「ライブラリ／ダウンロード／フォルダ」の絞り込み、曲名・人物・日付・再生回数順がある。

1. **再生・ダウンロード失敗の切り分けと表示**：同じアルバム保存曲で調査し、ログイン／内容確認／通信／保存失敗を区別する。ダウンロード準備段階も失敗項目として表示し再試行できるようにする。
2. **同期の送信範囲を確定して統一**：自動取得ON/OFF、取り込みのみ、双方向更新を別概念として明示する。読み取りのみなら全操作でYouTubeへの変更を0件にする。二重送信・確認前更新・失敗時の成功表示を修正する。
3. **登録由来と削除範囲**：アカウント、同期由来、手動登録を保持する。同じ曲が複数経路に属しても消し過ぎない設計にし、「アプリから外す」「ダウンロードを消す」「YouTubeにも反映」を区別する。アカウント切替・再同期時の除外維持も仕様に含める。
4. **検索対象の不一致を先に修正**：いいねだけの曲は一覧には出るが、アプリ内検索のSQLはライブラリ所属／ダウンロードのみを候補にする。空のプレイリストも名前検索から漏れる。検索条件を増やす前に、保存済みの対象を見つけられるようにする。
5. **検索条件を追加**：いいね／未いいね、ダウンロード済み／未ダウンロード、端末音源／YouTube、ライブラリ所属、プレイリスト所属。次に曲名・アーティスト・アルバムを別条件で組み合わせる。追加日・発売年・長さの範囲指定はその次。同期由来の条件は上記の記録整備後に追加する。

根拠：`viewmodels/LocalSearchViewModel.kt:26–58`、`ui/screens/search/OnlineSearchResult.kt:328`、`ui/screens/library/LibrarySongsScreen.kt:143,331,364`、`db/daos/SongsDao.kt:33–41,108–111`、`db/daos/PlaylistsDao.kt:64–77`、`db/entities/SongEntity.kt:29–56`。

アプリ内検索の「ローカル」は保存済みYouTube曲も含むが、DBのisLocalは端末音源を意味する。画面では「アプリ内」「端末の音楽」など意味を区別する。オンライン側の詳細条件はYouTube応答に存在する情報を確認し、取得済みの一部ページだけを除外して全件検索のように見せない。

## 検証結果と残る作業

- 確認済み：HEADに対する同期・登録・削除・検索・再生／ダウンロード経路のコード調査。過去テストを再実行せず、対象と限界を再確認。
- 確認済み：開発用アカウントの公式YouTube Musicログイン、アルバム記録のLithiumで内容確認後に再生時刻が進行、一時停止。
- 未確認：ユーザーが現在使う端末の保存済みID・音声実体とOuterTune内の再生。アカウントの外部更新を伴う同期操作の実行検証。
- 変更：本記録の追加のみ。ビルド・APK配布・DB操作・commit／pushなし。
- 文書確認：参照するファイルと相対リンクが存在し、末尾空白なし。`git diff --exit-code`で追跡済みの製品ファイルに差分なし。本記録だけが未追跡として追加されている。
- 次の一手：保存先端末を特定してダウンロード実体を確認し、問題の再生／取得経路を同一IDで記録する。検索・同期の製品仕様変更は上記の提案を起点に一課題ずつ扱う。
