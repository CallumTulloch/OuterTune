## 現象・範囲

- ユーザー確認: 前回APKでライブラリの約20秒の表示待ちは解消した。
- Imagine Dragons「bileaver」と報告されたアルバムを**検索から初めて開く**と、再生などをして約1分後に全体の名称が正しくなった。保存済みライブラリからの遷移ではない。
- 質問: 初回の高速化は可能か。保存一覧の表示改善後も名称解決は重いままか。曲数の増加で通信量・時間が増えないか。
- 最初は現行コードと既存検証記録を調査。その後、ユーザーの「はい，その方針でよいです」を受け、以下の範囲を実装・検証してAPKを生成した。
- 期待値: 保存表示と新規名称取得を区別し、待ち時間・対象数増加の要因と改善可能な範囲を説明する。
- 対象: `7e48d375` + 前回からの未コミット差分。ユーザーのアルバムID・実行ログは未取得。作品名から別の版のIDを推定しない。

## 改修前の調査で確認した事実

参照するコードは `app/src/main/java/com/dd3boh/outertune/` 以下。

1. `repositories/MetadataNameRepository.kt` の `start` は、検索・ホーム・キュー等の観測に含まれる曲・人物・アルバムを予約する。選択したアルバムだけが対象ではない。取得は共通FIFOの3ワーカーで、開いたアルバムや再生曲の優先度はない。
2. `captureAlbumOriginals` は曲ごとの原題確認を順に待つ。その後の `captureAlbumPlaylistReferences` でも別のsource IDの原題確認を順に行う。未取得N曲なら原題確認だけで概ねN件、別source IDがあれば追加取得が必要になる。通常のMusic名称取得には最大50曲のまとめ取得があるが、Main原題確認は曲ごとである。1分の固定待機はない。
3. `Runtime.albumContext` で取得したアルバムのheader/playlist IDは返却されず、`captureAlbumPlaylistReferences` がheaderを取り直す。同じ認証・locale・完全性を保った応答の共用により、重複通信を減らす余地がある。
4. `due` / `metadataRetryDelay` は保存した取得状態を利用する。成功は7日、失敗は5分、曲のEMPTYは5分、その他のEMPTYは24時間が再取得の目安。起動のたびに全曲へ再通信するわけではない。アルバムの証拠補強など別の再取得条件はある。
5. `refreshTargets` は全metadata targetとDB保存対象を走査する。起動・取得設定変更・5分ごとに呼ばれる。5分ごとの走査は全件への通信を意味しないが、未取得・失敗・期限切れの対象は通信を伴う。
6. `db/entities/MetadataTargetEntity.kt` には最終閲覧時刻がなく、`deleteMetadataTarget` のproduction呼出しもない。検索等で観測した対象も蓄積するため、ライブラリの曲数だけでなく過去の閲覧対象数でも走査量と更新対象数が増える。
7. `evaluateOriginals` と `OriginalAssessmentRetention.kt` は、保存された原題候補全体の指紋で判定結果の再利用可否を決める。新規原題で指紋が変わると、既存分を含む全候補の言語判定と表示用証拠の組立を再実行する。処理待ちの中間スナップショットは間引かれるが、アルバム単位の差分評価ではない。
8. 言語判定は `OriginalAlbumLanguageResolver` の端末内モデル。上記の全体再評価は主にCPU・DB負荷で、外部LLMへの送信ではない。原題確認の通信はplayer/next等のメタデータ応答であり、名前の短い文字列だけの取得ではない。この名称処理で音声本体を取得するわけではない。

## 前回改善との区別

[前回の最終記録](2026-09-27-library-startup-and-beatles-one.md)の2,000曲・106msは、保存済み名称の初回公開の測定。初めて開くアルバムの通信・判定が106msになったという意味ではない。

前回は初回表示の軽量化に加え、有効な保存判定の再利用とDB transaction外への証拠組立移動も行った。したがって、以前と全く同じ20秒の処理を隠しただけでもない。一方、未取得アルバムの逐次通信や取得優先度は改善していない。

既存のBeatles「1」27曲の実通信テストは22.251秒だったが、独立したテストであり、アプリのホーム・検索と同時に動く条件や今回のアルバムの実測値ではない。

## 改善候補と検証条件

優先順位は次のとおり。原題の根拠、ID対応、英語判定条件、証拠撤回時の整合性は維持する。

1. 表示中アルバム・再生曲を優先する。バックグラウンドの大量更新が先行していても待ち続けないようにする。通信の同時実行数には上限を保つ。
2. 過去に検索で見ただけの対象の定期更新を抑え、再閲覧時の更新や保存対象を保護したキャッシュ整理、失敗時の取得予算を設ける。
3. 同一条件で取得済みのアルバム応答を共用し、曲の原題確認も上限付きで並行処理する。IDごとの重複取得防止と欠損・競合時の回復を維持する。
4. 判定結果の失効と再計算を、変更したアルバム・共有人物など実際の依存範囲に限定する。無関係な新規曲で全体を再判定しない。

実装時は同じアルバムIDで、初回表示から名称確定まで、通信待ちと実行時間、要求件数・転送量、既存データ件数を記録する。大量の既存データ・検索履歴がある条件と再訪・再起動時の再利用を比較し、名前の正しさと通信増大の両方を検証する。

## 承認後の最終実装

対象ソースは `7e48d375` と既存・今回の未コミット差分。コミット、push、DB schema変更は行っていない。

- 画面の表示期間と再生中の曲IDを取得優先度へ反映。待機中の同じ要求を昇格し、保存対象の更新も飢餓状態にしない。
- 定期更新を登録・高評価・ダウンロード・保存プレイリスト・ブックマークとそれらの関連対象、および現在の画面・再生に限定。過去に閲覧しただけのDB行と名称キャッシュは保持し、定期全件再取得から外す。
- 原題取得を3曲ずつ並行処理し、MetadataNameRepositoryの通信同時実行上限も3に保つ。IDごとのmutexと最新状態の再検査は維持する。別のアルバムへ移った際は、直接取得・playlist確認・代替source検索の区切りで背景アルバムに処理を譲らせる。
- 同一条件の完全アルバム応答を短期間共用し、見出し・playlist IDの取り直しを削減する。
- 判定指紋を対象と同一アルバム曲の依存範囲へ限定。無関係な追加作品で保存済み評価を失効させない。既存形式からの初回のみ端末内の再評価が必要で、通信の再取得は要求しない。
- 画面・再生変更時は待機要求の優先度を更新して古い画面を降格。同一画面の継続通知では曲の優先対象を消さず、遅着した別画面の応答が現在の優先対象を上書きしないよう更新を同期する。
- 名前の根拠、曲IDの対応、言語の判定条件、証拠撤回、手動編集とローカルタグの優先規則は維持する。
