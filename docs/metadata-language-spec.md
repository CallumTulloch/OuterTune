## 合意済みの基本仕様

| 項目 | 期待する動作 |
| --- | --- |
| 対象 | オンラインの曲名・アルバム名・人物名を、種類と安定IDごとに扱う。 |
| 二言語の取得・保持 | 英語を常に取得・保持対象にし、コンテンツ言語が英語以外ならその言語も取得・保持する。表示設定のON/OFFで取得対象を変えない。 |
| OFF（初期値） | 設定されたコンテンツ言語の名前を優先する。 |
| ON | 「正式な原表記が英語なら英語を利用」。英語の原表記と判断できる名前は英語、それ以外はコンテンツ言語を使う。 |
| 判定対象 | 一曲が英語であるだけで、人物名・アルバム名・別の収録曲を一括して英語と認定しない。 |
| 判定材料 | 国籍・歌唱言語・Latin文字であることだけでは決めない。日本の作品でも正式な英語タイトルは英語として扱う。 |
| 短い名称 | 単独で判断しにくい場合は、確かな対応がある同一アルバムの原題群を補助材料にする。 |
| 検索 | ON/OFFにかかわらず英語とコンテンツ言語の情報を検索対象にする。表示に選ばれなかった名称も保持する。 |
| 共通表示 | 同じ種類・IDの取得済み名称は共通の選択結果を使う。検索・アルバム・ライブラリ・プレイヤーごとに別の英語優先規則を設けない。 |
| 元データ | 表示の切替でraw名称・クレジット・曲や人物のID・関連・再生URIを書き換えない。再生位置やキュー順も維持する。 |
| ローカル・手動 | 端末内の曲・アルバムのタグや手動改名を自動の言語選択で上書きしない。アーティスト紐付けによる表示投影は別機能として扱う。 |

「英語名が取得できた」と「正式な原表記が英語と判断できた」は別の状態。
ONは、英語候補が存在するものを無条件に英語へ変える設定ではない。

### UI言語とコンテンツ言語

- アプリのUI言語は、操作ラベルやメッセージの言語を決める。
- コンテンツ言語・地域は、名前を取得する要求と表示名の選択に使う。
- コンテンツの明示設定を優先し、「端末に従う」は実際の端末システム言語・地域を参照する。
- アプリUI言語だけの変更ではコンテンツ言語を変えない。端末変更は「端末に従う」場合に反映する。

### 未取得・失敗・競合時

- 設定言語の名前が未取得なら、英語候補だけで各画面の元表記を上書きせず、その項目が持つ表記を維持する。
- 配信元が指定言語でも英語を返す場合や通信失敗時に、日本語名を作ったり翻訳したりしない。
- 初回の原表記判断が不明・競合なら、裏付けのある英語として採用しない。初めて取得する対象は共通のコンテンツ言語候補を基準とし、確認完了による一度の英語切替を許容する。
- 確定済みの名称を再取得・再評価している間と、取得や評価に失敗した場合は、最後に確定した英語採用結果を保持する。評価待ちや失敗を、完成したUNKNOWN/OTHER判定として扱わない。
- 新しい原題、別言語、不明、競合、根拠撤回を示す判定が完成した時点で、対象の確定結果を更新する。古い英語採用を無期限に正解とせず、撤回後の再起動でも以前の証拠を復活させない。
- コンテンツ言語候補自体がまだ無い場合は取得済みの元表記を保ち、翻訳名を作らない。この不足と、保存済み確定表示を読み込む前の一時的な表示は区別する。

## 現行実装の詳細・制約

以下は実装の説明であり、取得方法や待機時間を固定するユーザー要件ではない。

1. `ContentLocaleRepository`がコンテンツ言語・地域と変更通知を一元化する。要求開始時の言語を後続ページにも保持し、古い言語・認証条件の応答を現在の表示へ混入させない。
2. `MetadataNameRepository`がAPI観測・詳細補完から名称を収集する。`metadata_name`は種類・ID・言語・名称・取得元を分け、`metadata_fetch`に取得状態を記録する。
3. 完成した原題評価と英語表示候補を`metadata_original_publication`へ保存する。表示はこの確定結果と現在の設定言語候補から共通選択し、`MetadataNames.resolve`を曲・アルバム・人物の表示拡張が参照する。手動名を優先し、設定言語の詳細候補と一覧等の候補は取得元の優先度・観測時刻で選ぶ。

英語の表示候補には、詳細優先の例外を設ける。同じ種類・IDの評価が示す原表記が一つに揃い、それに一致する取得済みの英語候補がある場合は、その候補を詳細応答より先に採用規則へ渡す。そこで引き続き英語の原表記と判断できることを要求し、UNKNOWN・OTHER・競合を理由なく英語化しない。評価の文字列だけから未取得の名称を作らず、手動名、設定言語の候補選択、OFF時の優先順位も変えない。

9/27追記: 一致するMusic英語候補がない場合も、同じIDの直接原題または検証済みのID参照に保存された実取得Main原題を、そのまま採用候補にできる。例は「1」の `Eleanor Rigby (Remastered 2015)`。Musicの `Eleanor Rigby` と差があるため、Main原題の版名も保持する。任意のund行や判定結果だけから名称を生成せず、括弧の除去や翻訳もしない。英語・競合の最終採用規則は共通とする。

実機の保存データでは、`In Bloom`の英語詳細名が`In Bloom (Official Music Video)`、英語アルバム候補が`In Bloom`だった。詳細応答の優先度は、動画用の付記を含む名前まで正式な原表記であると保証するものではない。このため確認済み原題と一致する取得済み候補を選び、`Official Music Video`などの文字列を機械的に除去して原題を作る処理は行わない。

### 確定結果の保存と画面への公開

DB version 29で`metadata_original_publication`を追加する。種類・対象IDごとに、採用できる英語名（採用しない確定結果はnull）、判断に使った原題・参照の証拠、評価時刻を保持する。従来の名称候補と取得状態は別に維持し、この表をraw名称や人物・曲の関連の保存先にしない。DB version・schema JSON・初期化方針を同時に管理し、既存データ移行不要のプロジェクト条件を維持する。

- 原情報や英語候補は取得に応じて保存できるが、新候補と以前の判定を組み合わせて新しい英語名を公開しない。評価結果と、それに基づく具体的な英語表示名・証拠を同一トランザクションで確定する。
- 評価対象の一部について判定器の出力がない場合は未完了とする。全入力を処理したUNKNOWN/OTHERや競合とは区別し、既存の確定結果を残す。DB上で原題証拠が明示的に撤回・削除された場合は、以前の対象も含めて確定結果を更新する。Main応答のタイトルや説明の欠損から、直接原題の消失を推測する処理ではない。
- 保存前に、原題・観測時刻・英語候補・参照証拠の世代を照合する。処理中に変化した入力へ遅い評価を保存しない。手動名の更新は直接表示へ反映し、言語判定の再実行条件にはしない。
- 直接原題の全入力と判定器バージョンの指紋が一致し、保存済み評価がすべて有効なら、再起動後も再利用できる。観測時刻だけの更新でモデルを再実行しない。原題・文脈・判定器の変更で指紋が変わる場合は再評価する。
- OFFは現在のコンテンツ言語候補へ即時に戻り、ONは保存済みの確定英語名を使用する。コンテンツ言語変更も取得・評価の完了を待たずに再選択する。英語候補の保存・両言語検索はON/OFFと独立させる。
- 起動時は名称候補と確定結果をDBから一緒に読み込み、最初の共通表示を公開してから通常の画面内容を出す。この初期読込だけを待ち、新しい通信や初回の原題評価は画面表示の待機条件にしない。保存済みの有効な評価だけがあり確定結果が空の場合は、そのDBスナップショットから作成できる完成済み結果を使う。
- 通常の表示読込は証拠JSONを除いた単一JOINクエリを使う。初回表示後に名称取得・評価を開始する。証拠の解析と確定結果の組立はDBトランザクションの外で行い、保存直前に入力と前回確定結果の世代を照合する。変更のない確定結果は書き直さない。

この保存と公開の分離は、「処理中は以前の確定表示を維持する」ための仕組みであり、期限切れの根拠を新しい根拠として認定するものではない。最終画面だけでなく、評価を止めた状態・再起動・別作品追加時の公開履歴を検証する。

### 原題の取得経路

通常の曲補完は従来どおり、英語のMusic詳細応答で同じ動画IDの`MUSIC_VIDEO_TYPE_ATV`（Art Track）を確認し、YouTube Mainの原情報を取得する。確認済み英語SongItemを保持していなければ原題取得時にも`getQueue`を使う。

これとは別に、対象アルバムの英語の全曲ページを直接取得し、要求したアルバムID・応答のアルバムID・各曲の所属IDを確認してから、各動画IDのMain原情報を取得する経路を持つ。この経路は`getQueue`の成功に依存しない。英語アルバム応答は名称候補と収録関係の根拠であり、英語の名称候補そのものを配信原題とは認定しない。

アルバム専用の照合では、次をすべて満たした場合にMain原題を候補として扱う。

- 正規ページから直接得た曲とMainの動画IDが一致し、有効な動画ID・アルバムIDを持つ。旧DBの収録関係、同名検索結果、表示順からこの対応を作らない。
- Mainの説明文が、配信元を示す`Provided to YouTube by ...`、原題とクレジット、空でない単一行のアルバム名、末尾の`Auto-generated by YouTube.`を持つ構造である。原題とクレジット行の先頭が一致する。
- watch endpointが別の動画IDを示さず、明示された動画種別がATV以外ではない。再生制限等でendpointが欠ける場合は、この正規アルバム由来の専用経路でのみ許容する。

曲の原題はMainの同じ動画IDに結び付け、言語判定に使うアルバム所属は直接取得したページのIDを根拠にする。Mainが通常版名、ページが別版名を示す場合も、この収録関係と曲原題は保持する。アルバム名そのものの原表記候補は、Mainのアルバム行とページの英語名が完全一致するときだけ生成する。版名の除去・翻訳・曖昧な正規化で一致させない。

同じ参照元動画ID・同じ原題を再取得し、既に一意の確認済みアルバム文脈がある場合は、その文脈を保持する。期限切れ後に別版のページから同じ動画を取得した場合や、キュー応答でアルバムが省略された場合も、既存文脈の撤回とは解釈しない。原題自体が変わる場合はこの保持条件を満たさず、新しい証拠を評価する。

原題候補を認定するためのMainタイトル・説明の必要条件が欠ける場合は、取得を未完了として再試行する。HTTP成功や空の候補集合だけで、保存済みの直接原題へ撤回記録を書かない。原題の原情報と確定表示は保持し、新しい十分な原題証拠を取得できた場合に更新する。通常経路で必要な同一IDのArt Track情報が得られない場合も、別IDや同名曲で補わない。

別版から同じ原題を再取得したとき、今回の完全なMain説明で以前のアルバム名が再確認できれば、その既知のアルバムIDの原題証拠を保持する。人物は今回Musicの同じIDと名前も要求する。既存の人物・アルバム証拠がある状態でMusic側のID欄が欠ける場合は不完全な取得として扱い、欠損だけで旧証拠を撤回しない。

人物の候補は、オンラインIDを持つ既知のクレジット全体とMainの原題・クレジット行が完全一致するときだけ生成する。投稿チャンネル名から人物を認定したり、区切り文字で人物名やIDを作ったりしない。これらは原題候補の取得条件であり、英語表示には以下の言語評価も必要。

### Mainの曲カードによる別動画IDへの曲名参照

配信元が通常のアルバム曲目にも公式動画（OMV）のIDを返す場合がある。その動画自身から配信原題を取得できないときは、確認済みArt Trackを参照元とし、Mainが明示する曲カードのリンクを曲名表示の根拠として利用できる。これは同一録音の認定やIDの統合ではなく、曲名に限定した一方向の参照である。

`YouTube.mainSongReference`は指定した言語・地域で匿名のMain WEB `next`を取得する。MusicのCookie・visitor・アカウント情報を送らず、次の条件を満たす応答だけを扱う。

- `currentVideoEndpoint.watchEndpoint.videoId`が要求した参照元動画IDと完全一致する。省略・別IDなら採用しない。
- `engagementPanels[].engagementPanelSectionListRenderer.content.structuredDescriptionContentRenderer.items[].horizontalCardListRenderer.cards[]`内の`videoAttributeViewModel`が、全対象パネルを通してちょうど1件ある。endpointのない2件目も曖昧として拒否する。
- そのカードの`onTap.innertubeCommand.watchEndpoint.videoId`が有効な11文字の別動画IDである。推薦欄、URL文字列、任意の入れ子から代わりのリンクを探さない。

カードの解析は「有効な参照」「完全な説明を確認したがカードなし」「不完全・不正で確認不能」を分ける。要求元ID違い、構造化説明の欠落、途中の説明、壊れたカード、endpoint欠損、複数カードは`Result.failure`とし、旧参照を撤回しない。`Result.success(null)`は、要求元IDが一致し、認識済みの説明構造に空でない見出しと本文が揃い、追加取得の兆候がなく、その完全な説明に音楽カードがない場合だけ返す。説明パネルの欠落や、存在するカード欄の内容欠損を、正常なカード消失として扱わない。

カードの名前は翻訳される可能性があり、原題や原言語の証拠にはしない。参照元には既存経路で照合した同IDのArt Track原題とアルバム文脈を要求する。参照先は、観測済みの英語Music候補がその原題に一致し、所属アルバムIDも一致することを制約とする。検索や保存済みの同名・同アルバムは候補を絞る材料にすぎず、動画間の対応を成立させるのはMainの明示リンクである。比較では前後空白とUnicode NFC以外の大小文字・記号・版名を推測で揃えない。

`ProviderSongReference`は参照元・参照先ID、原題、参照元アルバムID、原情報の指紋を、`main-song-reference:<参照元ID>`の別証跡として保存する。確定結果の作成時には、最新の参照元原題と指紋が一致し、現行判定器・全評価入力に対して有効な直接取得の評価がある場合だけ、その評価をメモリ上で参照先の曲名選択に渡す。参照元の評価がENGLISHであることと、参照先の英語候補との整合が必要であり、英語候補の存在だけでは英語化しない。直接取得の評価と競合する場合も既存の保守的な採用規則に従う。評価待ちの画面は前節の保存済み確定結果を参照する。

参照先を新たな原題候補として判定器に渡さず、アルバム文脈の曲数を増やさない。別IDに読み替えた評価を直接取得の原題JSONとして保存せず、直接取得における「対象曲ID＝参照元動画ID」の制約を維持する。参照を次の参照元に使う推移的な引き継ぎもしない。曲・人物・アルバムのID、収録関係、raw名称、再生内容は変えず、人物名・アルバム名への派生も行わない。手動名とローカルタグの保護は共通表示の規則を維持する。

取得中のアルバムでは、直接原題を得られないOMV行について同じアルバムの既存原題を先に確認し、不足時は曲検索からATV候補を探す。候補が見つかっても、原題の照合とMainの明示リンクを省略しない。保存済みデータも、起動時・定期再予約時・原題評価更新後に、オンライン曲のアルバムIDと取得済み英語候補から参照を再点検する。最高優先度の詳細名だけでなく、同じ対象IDに観測済みの英語別名のいずれかが原題に一致すれば候補を検討するが、アルバムID・検証済み参照元・Mainの明示リンクは必須のままとする。この復旧は既知の直接原題を使い、配信元が過去と同じ曲ID一覧を再び返すことを条件にしない。ローカル曲は対象外とする。

曲カードの取得状態は参照元動画IDと`main-song-card:<地域>:v1`で記録し、成功の再取得間隔は7日、空結果・失敗は5分とする。保存済み曲がなくページだけで観測した対象も、既存参照があっても補完処理ではこの取得間隔を確認する。参照元の原題やアルバム文脈が変わった成功記録は、そのまま待機の根拠にしない。原題取得と同じ参照元mutexを使い、応答後と保存時に要求条件・最新原題を再確認する。

同名の別候補を調べた結果、カードが別の動画IDを指していても、参照元全体をEMPTYにはしない。観測したカードの参照先と一致する既存参照は保持し、正しい対象の確認を待機で妨げない。上記の完全な説明によってカードなしを確認できた場合や、有効なカードが旧参照と異なる参照先を明示した場合は、該当する旧参照の証跡を明示的な`{}`に更新して撤回する。不一致候補の確認だけで、既に無効な撤回記録の観測時刻を更新しない。名称は検索別名として残す。一般の名称保存では`null`証跡が「既存証跡を保持」を意味するため、撤回には使わない。通信失敗や不完全・不正な応答だけでは旧参照を撤回せず、最新の無効な参照を飛ばして過去の有効な参照を復活させることもしない。

### 同じプレイリスト項目IDによる別動画IDへの曲名参照

9/20の追加経路では、正規アルバム見出しのplaylist IDを根拠に、同じ要求条件のMusic `browse(VL...)`と`next`を取得する。両応答にある`playlistSetVideoId`をplaylist IDの範囲内で照合し、音源用IDと通常一覧のIDを対応付ける。タイトル、曲順、動画種別、検索順位は対応のキーにしない。名称参照の対象をOMV型だけに限定せず、原題を取得する参照元の構造・ID照合は従来どおり必要とする。

- 要求先のplaylist ID、browseの対象、nextのpanel・current endpoint・各行endpointを照合する。項目IDと動画IDの重複、項目集合の不一致、違うplaylistを示す応答、不完全な応答は成功としない。
- 参照元には同じ動画IDに対する直接原題と確認済みアルバム文脈を要求する。参照先のアルバムは、今回確認した正規アルバムのplaylistに結び付ける。同じ音源IDが別版にも収録される場合があるため、参照元の言語評価に使ったアルバムと、今回の参照先アルバムは一致を要求せず、別々に検証・保持する。
- 参照先には、そのIDに対して別途取得した英語候補を要求する。原題との完全一致、または同じ正規playlist内のsource/targetから独立に取得したMusic名の完全一致で表記を照合する。後者ではsource MusicのID・endpoint・albumも確認し、Mainの正式原題は未加工で保持する。名前の一致だけでID対応を作らず、再生制限でnextに名前が無い場合も、別途取得したtarget英語候補が必要。
- `playlist-song-reference:<参照元ID>:<playlist ID>`の証拠形式v3に、項目ID、両動画ID、原題、`sourceMusicName`、`sourceAlbumId`、`targetAlbumId`、原情報・対応全体の指紋を保存する。形式v2の完全一致参照は互換読込する。形式v1は流用しない。直接原題のJSONとは分離し、最新の直接評価から曲名の確定結果を作る。参照先は判定器の追加票にも次の参照元にもせず、再生ID・曲順・人物・アルバムの名前や関連を変更しない。アルバム再取得キーv5で既存キャッシュも新しい照合条件を再確認する。
- 完全な項目応答で対応が消えたり変わった場合は旧参照を明示的に撤回する。通信失敗や解析できない部分応答では、以前の参照を「消えた」と解釈しない。参照元の原題や英語候補が不足している曲は確認未完了として残す。
- **continuationは検証済みの応答連鎖だけを取得する。** browse/nextの初回応答から発行されたtokenを順番に追跡し、続きの応答でもplaylistの範囲、項目ID、動画ID、endpointを検証する。tokenのループ、重複、欠落、別playlist、途中通信失敗、100ページまたは10,000項目を超える応答は成功扱いせず、保存済み確定表示を保持してアルバム確認を未完了にする。全ページの安定項目集合が一致した場合だけ既存の単一ページ経路と同じ参照証拠を作る。長い作品の実通信での全曲確認は別途記録する。

Nevermindの全13項目で対応が得られた調査は、この限定経路の根拠である。一般作品での安全性、全曲の原題・言語確認、実画面改善はそれぞれ別の検証対象とする。

### 全曲補完の対象と取得状態

自動の全曲原題補完は、ブックマーク、ライブラリ登録曲、ダウンロード対象曲を持つオンラインアルバムに加え、全曲ページの応答を実際に観測したアルバムを対象にする。観測条件は`source="album"`の応答内に、そのアルバムIDを持つ曲とアルバム見出しがあること。アルバム画面に限らず、統計画面等の全曲取得もこの条件を満たす。検索結果、見出しだけの補完、キューの仮アルバム登録だけでは全曲展開しない。

ページ観測による追加対象はプロセス内で要求の認証・地域条件とともに保持し、条件変更時に古い対象を除く。画面のSTARTED期間は開いているアルバムを明示的に優先し、再生中のオンライン曲も優先する。未保存アルバムは再起動後のページ再取得・観測によって再び対象になる。取得前後と保存トランザクション内で要求の有効性を検査し、古い条件の応答を現在の取得結果として保存しない。

9/27の負荷対策では、定期更新は保存・高評価・ダウンロード対象曲、保存プレイリストの曲、ブックマークしたアルバム・人物とそれらの関連対象、および現在の画面・再生対象に限定する。検索や過去の閲覧で記録しただけの名称・DB行は残すが、起動時や5分ごとの全件再取得対象にしない。再閲覧時の観測から必要な取得を予約する。取得待ちは優先度付きで共有し、前景3バッチごとに背景にも機会を与える。原題確認は3曲ずつ並行し、名称処理全体の同時通信も3件に制限する。正規のアルバム応答は認証・地域・言語が同じ場合に限り60秒、最大32件共用する。

- アルバム補完の状態キーは`album-original-context:<Music要求条件>:v5`。v2は英語曲目の取得とMain原題取得の区別、v3は曲カード参照の確認を追加したもの。v4では動画種別を問わず安定したプレイリスト項目の対応も確認し、v5では独立取得したMusic別名を介した正式原題の照合を追加した。項目対応経路の取得状態は`album-playlist-reference:<Music要求条件>:v1`に分ける。
- 英語曲目の保存時点ではアルバムをSUCCESSにしない。空でない曲目について、各曲のMain原題取得が成功するか、現在の原題に結び付く曲カード／プレイリスト項目参照の取得が必要になる。曲カードは同地域の7日以内のSUCCESS、プレイリストは今回の対応と参照元確認が全件完了したことを要求する。一部失敗・空結果・不完全な追加項目応答はアルバム全体をFAILEDにし、現在の曲目が直接確認済み音源だけでも、追加の別ID対応に未確認が残る場合をSUCCESSにしない。
- 途中終了や参照の再取得失敗を7日間の成功扱いにせず、既存の確定表示を維持しながら5分後の再試行対象とする。取得完了は全名称の英語判定・英語表示を意味しない。
- 曲の原題が既にSUCCESSでも、有効なアルバムIDが原題の文脈に無ければ、7日の取得間隔内でも再取得して補完する。別版を含む確認済みのアルバム文脈が既にあればSUCCESSの待機期間を維持し、同じ動画IDが別のアルバムページに現れただけでは再取得して既存の原表記根拠を置き換えない。待機期間後の実際の再取得でも、同じ動画ID・原題なら既存の確認済み文脈を保持する。
- 通常の原題補完とアルバム補完は、動画IDに対応する固定数のmutexを共有する。同じ曲の取得、成功保存、失敗状態の記録を直列化し、遅れて処理した失敗が別経路の成功を上書きしないようにする。

現在の基本再試行間隔は次のとおり。これは実装上の取得制御であり、表示仕様として固定する待機時間ではない。

| 状態・対象 | 再取得可能になるまでの間隔 |
| --- | --- |
| SUCCESS | 7日 |
| SONGのEMPTY（曲詳細・Main原題） | 5分 |
| SONG以外のEMPTY | 24時間 |
| FAILED等 | 5分 |
| PENDING | 待機なし |

アルバム経路は、既存の曲単位のEMPTY・FAILEDが残っていても、正規ページを根拠にした最初の原題確認を試せる。その経路で再び失敗・空結果となった曲は、プロセス内の5分待機で繰り返しを抑える。保存されたアルバムのFAILEDにも再試行間隔があるため、再起動が常に即時の再取得を意味するわけではない。取得対象の定期再予約は5分ごとに行う。

### 自動評価と再取得時の保持

原題候補は`und`として保存し、原情報と自動言語評価を分離する。対象ID・原題・参照動画・方法・確度・入力指紋・評価時刻・versionを保持する。現判定器は`langid-java`を使い、元表記と小文字化の双方を評価する。個別判定は0.90以上、アルバム文脈は異なる曲IDの原題3件以上・0.95以上が条件。明確な非英語や競合を含む文脈は、曖昧な短題の英語化に使わない。

表示採用には、その対象の英語候補と原題評価の名称が整合することも必要。自動ENGLISH評価は人による確認済み根拠と同一ではなく、旧形式や対象違いの評価は流用しない。日本語の原題を英語APIがローマ字で返す場合も、英語候補だけで原題を置換しない。

同じ原情報の再取得で有効な評価を一時的に消さないため、評価JSONには依存範囲の指紋も記録する。9/27以降の形式v2は対象候補、同じ対象IDの候補群、所属アルバム内の全曲原題を含む。種類・対象ID・名称・参照動画ID・アルバムIDと判定器の版を含み、観測時刻や入力順は意味上の入力に含めない。無関係な作品の追加・削除で保存済み評価を失効させず、必要なアルバム文脈を含めて未評価分だけを判定器へ渡す。旧形式は初回のみ端末内で再評価する。

評価を引き継げるのは、同じ参照動画の完全な最新候補集合が変わらず、その評価の依存範囲とモデルも一致するときだけ。原題・所属・同じ対象のクレジット候補の変更や消失、同じアルバムの文脈の追加・削除、不完全な取得元snapshot、古い観測、旧版・指紋の記録がない評価は再取得時の保持対象にしない。変更のない再取得では評価時刻も保持する。判定中に別作品が追加されても、依存範囲が現時点と一致する完成評価だけは最新行へ保持できる。ただし表示の確定結果は古い全体snapshotから公開せず、最新入力を再取得して整合を確認してから一括更新する。

この保持判定へ渡す新しい原情報と、証拠不足で新しい原題を認定できない応答は区別する。Mainの必要な項目が欠けた空候補取得は、旧snapshotの消失や明示撤回を意味しない。再試行待ちでは旧原情報を残す。同じ原題の再取得で既存の確認済みアルバム文脈を保持した場合は、その保持後の候補集合を使って評価の有効性を確認する。

保持判定は最新DBの読み取りと保存を同一トランザクション内で行う。非同期の再評価結果も、処理中に原情報や観測時刻が変わっていないことを保存直前に確認する。過去の名称は検索別名として残せるが、最新の参照動画snapshotから外れた関連を現在の評価根拠として復活させない。原情報内の評価を保持できない場合も、別に保存した表示の確定結果は新しい評価の完了まで保持する。raw名称・手動名・ローカルタグ・IDは変更しない。9/19の評価保持だけの変更はschema変更なしだったが、9/20の確定結果保存には前述のDB29を使用する。
