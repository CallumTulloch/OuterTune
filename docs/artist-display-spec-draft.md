# アーティスト表示・後着情報の反映：仕様案

2026-09-06に作成したユーザーとの検討資料。2026-09-07の実装指示に基づき、この資料の曲アーティスト処理を実装する。
実装・検証状況は[実装記録](verification/records/2026-09-07-artist-implementation.md)を参照。以下の説明や対応表だけを、動作確認済みという意味に使わない。
2026-09-07追記：第10節に、初回オンラインIDなしの解析結果・後着ID・DB登録・画面表示の対応表を追加。
調査時のコードは `40212b39`。根拠は [変更前のコードの整理](artist-current-behavior.md) と
[2026-09-05の実応答調査](verification/records/2026-09-05-artist-response-investigation.md)。

## 1. 目的

検索直後にオンラインIDがない曲でも名前を表示し、後から分かった個別名・移動先を、検索結果、プレイヤー、保存済みの曲へ共通して反映する。
検索結果や再生開始を追加取得の完了まで待たせない。取得しても個別名やIDを確認できない場合は、確認できた範囲のまま使えるようにする。
今回の対象は、YouTube Musicで「曲」として取得する音楽トラック。
2026-09-07のユーザー指定により、動画由来の曲でアルバムなどの情報が欠けるケースは今回の改修から切り離す。
ユーザーが動画由来の曲でその可能性を確認したとの報告に基づく範囲整理であり、こちらで端末検証した結果とは扱わない。
オンラインIDがない曲を、それだけで動画由来として対象外にしない。
2026-09-12の実データ調査と修正APKの依頼により、動画由来でも元のアーティスト表記・採用済み人物がともに空の場合は、同一動画IDの個別曲情報から表記を回復する対象に含める。
この基本情報の取得を理由に人物ページや演奏者クレジットへ探索を広げない。既存の非空表記と動画種別の根拠を保持し、アルバムの人物を曲へ推測で流用しない。
フォルダ音源のタグ分割規則も別課題であり、この案で変更したものとは扱わない。

現在は検索結果を再生用データへコピーし、ライブラリは別にDBから読むため、DBを更新するだけでは表示は揃わない。
この案は画面の文言修正だけでなく、同じ曲が使う情報と更新の仕組みを共通にする変更を必要とする。

## 2. 三つの情報を独立して扱う

| 情報 | 例 | 意味 |
| --- | --- | --- |
| 元の表示 | `翟锦彦、8082Audio` | 曲の応答が返した表示文字列。人物数の証明にはしない |
| 個別に確認できた曲のアーティスト一覧 | `[翟锦彦, 8082Audio]` | 表示順と曲への関係を持つ個別項目。オンラインIDは必須にしない |
| 各項目の移動先 | 内部ID、確認済みのオンラインID | 名前を表示できることと、外部ページを開けることを区別する |

元表示・取得元・言語・曲IDを保存し、解析後に捨てない。個別項目には内部参照、曲での表記、役割・取得根拠を持たせる。
画像取得時に判明したアーティストページ名は、曲に付いていた表示名とは別に扱う。

名前の状態は「表示のみ／一部の個別名を採用済みで一覧全体は未確定／個別一覧全体を採用済み／情報が競合」、オンラインIDの状態は各個別項目ごとに「未確認／対応確認済み」とする。
通信の状態（未取得・取得中・成功だが追加情報なし・失敗）は別に持つ。
`IDなし` は、名前不明・人物未分離・通信失敗のどれとも同義にしない。

### 用語と、個別名・オンラインIDの組合せ

この資料の「オンラインID」は、YouTube Musicのアーティストページを識別する値を指す。
曲を識別する曲IDと、アプリが個別アーティストの項目に付ける内部IDとは別の値である。
「オンラインID未確認」は、アプリが対象アーティストとの対応を確認できていない状態であり、YouTube Music上にページが存在しないとの断定ではない。
アーティストには個人とグループを含むため、確認前の結合文字列に対して「二人」「もう一人」とは記述しない。

「個別名を採用済み」は、その曲のアーティストとして扱う根拠を確認し、独立した項目として採用した状態を指す。
候補名を見つけただけの状態とは区別する。クレジットを根拠に採用する条件は第7節の未確定事項を含む。
「オンラインIDの対応を確認済み」は、その個別項目が指すアーティストと、オンラインIDが指すアーティストページの対象が一致すると確認した状態を指す。
名前の一部分が一致すること、曲メニューにページへのリンクがあること、候補IDの個数が名前の個数に一致することだけでは、個別項目への対応を確定しない。

まず、曲のアーティストとして個別名「A」「B」の二項目を既に採用している場合を、次の四通りに分ける。
「A」「B」は説明用の仮名であり、ここでは項目間の表示区切りを `、` とする。

| AのオンラインID | BのオンラインID | 検索結果・プレイヤー・保存済みの曲一覧のアーティスト名部分 | 個別項目に保存するオンラインID |
| --- | --- | --- | --- |
| 未確認 | 未確認 | `A、B` | AにもBにも、確認済みのオンラインIDを保存しない |
| 確認済み | 未確認 | `A、B` | Aの項目にAのオンラインIDを保存する。Bの項目のオンラインIDは未確認のままにする |
| 未確認 | 確認済み | `A、B` | Bの項目にBのオンラインIDを保存する。Aの項目のオンラインIDは未確認のままにする |
| 確認済み | 確認済み | `A、B` | Aの項目にAのオンラインID、Bの項目にBのオンラインIDを保存する |

四通りとも、曲に関連する個別アーティストの項目はAとBの二項目である。オンラインIDが未確認であることを理由に、名前の表示や曲との関連を削除しない。
未確認の候補IDが一つ以上手元にあっても、対応を確認できた項目だけを上表の「確認済み」と数える。
IDを得る順番は固定しない。初回検索で片方または両方の対応が確認できる場合にも、この表を適用する。

次の場合は、上表の「個別名A・Bを二項目として採用済み」という前提を満たすか、別途確認する必要がある。

| 取得した情報 | 名前の表示と、オンラインIDの扱い |
| --- | --- |
| 元の文字列 `A、B` だけで、個別名をまだ確認できない | 曲名下のアーティスト名部分には `A、B` を表示する。二つの個別名には分割しない |
| 元の文字列 `A、B` と、曲メニューから得た一つ以上のページIDがある | 曲名下のアーティスト名部分には `A、B` を表示する。メニューのページは候補として別に扱い、文字列の一部分へIDを割り当てない |
| `A、B` という一つの名前項目に、オンラインIDが直接付いている | 名前全体と、その名前項目に付いていたオンラインIDとの組合せを保持する。記号だけでA・Bに分割したり、オンラインIDを一部分へ付け替えたりしない。曲メニューにIDがあるだけの応答とは区別する |
| 元の文字列に含まれる個別名の一部だけを確認でき、残りの個別名や項目数が未確認 | 曲名下には元の文字列全体を表示する。確認済みの名前は曲のアーティスト情報で示せるが、未確認部分を削除したり、残りを一名と断定したりしない |
| 個別名A・Bは採用済みだが、取得した候補IDがAとBのどちらに対応するか未確認 | 曲名下のアーティスト名部分には `A、B` を表示する。候補IDは、Aの項目にもBの項目にも確認済みオンラインIDとして保存しない |
| 個別名またはオンラインIDの対応について、確認済みの情報どうしが矛盾する | 元の応答と矛盾した情報を記録する。新しい応答だけを理由に、既に採用した名前や対応IDを上書きしない。詳細は第6節を適用する |

元の文字列も個別名も取得できない場合の「アーティスト不明」表示、通信失敗時の扱いは第3節を適用する。

## 3. 表記の共通ルール

同じ曲ID・同じアプリ表示言語・同じ採用状態なら、1〜3の曲名下に使うアーティスト文字列を同じ規則で作る。
曲名、アルバム名、長さなど、行の他の要素や表示幅による省略は画面に応じてよい。

- 個別一覧が未確定で元表示がある：元表示をそのまま表示する。推測で切らない。
- 個別一覧を採用済み：各名前の内部の文字・記号を保持し、項目間だけ共通の表示区切りを使う。案として日本語UIでは `、` を使う。
- 個別名は分かったがオンラインIDがない：その名前も省略せず表示する。
- 採用済みの個別項目についてオンラインIDの対応だけが後から確認できた：曲に関連する名前・項目数・表示順を維持し、その個別項目にオンラインIDを保存する。そのアーティストのオンラインページと画像取得を利用可能にする。
- 元表示も個別名もない：名前の部分だけ「アーティスト不明」を表示する。確認できれば差し替える。
- 取得中・失敗時：直前の名前を維持し、行を空欄や読み込み表示で置き換えない。曲一覧に内部IDや解決段階を表示しない。
- 画像・オンラインページ名が後から届いても、それだけで曲名下の表示をそのページ名へ上書きしない。
- 言語による正常な表記差を許す。英語で取得したキャッシュを、日本語の表示名へ無条件に上書きしない。

`Earth, Wind & Fire` は一つの名前として保持され、その内部のカンマや `&` は表示区切りへ変換しない。

## 4. 画面ごとの表示と操作

| 画面 | 名前の表示 | アーティストへ移動する操作 |
| --- | --- | --- |
| 1. オンライン検索結果の各曲 | 共通ルールで作る曲のアーティスト表記 | 行タップは従来の再生操作を維持。曲メニューから個別アーティストを選ぶ |
| 2. プレイヤー | 第3節の共通規則で作ったアーティスト名の文字列を表示する。個別一覧が分かれば名前ごとに選択可能 | 個別名を選択して対応するアーティスト画面へ。オンラインIDなしでも内部ページを開ける |
| 3a. 曲一覧・ライブラリ内の曲・端末内検索 | 共通ルールで作る表記。保存した最新情報を利用 | 行タップは再生。曲メニューの人物候補は検索・プレイヤーと共通 |
| アルバム画面内の各曲 | 各曲について共通規則で作るアーティスト名の文字列を表示する | 曲ごとのメニューの個別候補を検索・プレイヤーと共通にする |
| 3b. ライブラリのアーティスト一覧 | 個別に確認して登録した人物・グループを一項目ずつ表示 | オンラインIDなしでも内部ページを開ける。画像なしは標準アイコン |
| 補助：キュー・通知 | 同じ曲の採用済み表記を反映 | 各画面の既存操作を維持 |

ここで1と3aは、文字列を作る規則は同じ。ただし、検索の返却オブジェクトとDBをそのまま別々に読む方式では一致を保証できないため、共通状態を参照する。
3bは曲名下の表記ではなく人物の一覧である。未分離の `A、B` を一人の人物として一覧へ登録しない。
曲自体のライブラリ保存は未分離でも可能とし、その曲の元表示を維持する。

### 個別名がまだ分からない状態での操作

プレイヤーの結合表示や曲メニューからは、その曲の「アーティスト情報」を開く案とする。
確認済みの個別候補があれば表示し、なければ元の表記・取得したクレジットを示す。取得中はこの画面で簡単に案内する。
別メニューから確認したオンラインページ候補は、実ページ名を使う独立した候補として表示できるが、結合名の一部へ推測で割り当てない。
未分離の結合表示そのものを人物ページへのリンクにはしない。

### オンラインIDがない個別名の内部ページ

- 名前、ライブラリに登録済みの関連曲・アルバムを表示する。
- 2026-09-07の追加ユーザー決定: `Songs opened from`／`このアーティストを選択した曲`の追加欄は削除する。未保存曲から人物ページを開ける機能は維持するが、選択元の曲や閲覧したオンライン曲の追加一覧は表示しない。既存の曲3件プレビューと全曲への入口を維持する。経緯は[追加欄の調査記録](verification/records/2026-09-07-artist-source-songs-investigation.md)を参照。
- ページを開いたことや内部参照の確保で、曲のライブラリ登録・いいね・ダウンロードを行わない。
- 確認済みの外部IDがあれば既存のオンライン表示も利用可能にする。IDなしでは内部表示から始める。
- 外部IDが後から確認できても、開いている内部ページを勝手にオンライン表示へ切り替えない。移動先の追加だけを反映する。
- 内部参照は維持して外部IDを追加する。ID補完時に人物や曲との関連を作り直さない。

## 5. 検索直後からの時系列

1. 検索応答を受け取る。同じ曲IDについて以前に確認済みの情報があれば取り込み、結果をすぐ表示する。
2. 名前の欠損、個別名のID未確認、未分離の表示など、追加確認に意味がある曲を抽出する。
3. 現在表示中の未解決行について裏で必要な情報を取得する。再生・保存・人物選択・ダウンロードの対象曲は優先する。
4. 採用できる情報が得られたら、その曲の共通状態を更新する。表示中の検索行も更新し、検索し直しを要求しない。
5. 再生を始めた時点で未解決でも、検索時の状態と進行中の取得を引き継ぐ。再生を待たせず、取得が終わればプレイヤー・キュー・通知へ反映する。
6. ライブラリ保存は名前の解決を待たず実行できる。後から採用した情報は同じ保存曲へ反映し、再登録を要求しない。
7. 再起動後は保存済みの採用情報から始める。検索で一時的に情報の薄い応答が返っても、保存済みの確かな個別一覧を元の結合表示へ戻さない。

**「検索後、表示中に補完する」ことは可能だが、「初回の検索応答だけで必ず全員のIDを得る」ことは保証できない。**
外部情報がない、通信に失敗する、対応が確認できない場合は、その状態でも表示・再生・保存・内部ページを使えるようにする。

### 追加取得の範囲と待ち時間

- 既知の曲は確認済みの状態を再利用し、画面ごとに同じ通信を繰り返さない。
- 名前も必要な対応IDも揃う通常曲は、今回の問題のための追加通信を行わない。
- まず同じ曲IDのキュー情報などから、不足が埋まるか調べる。対象曲のようにキューも結合表示なら、必要な曲についてクレジットを調べる。
- 人物ページは、応答にある候補IDの対応確認や画像取得に必要な分だけ取得する。人物名の一般検索を各行で繰り返す方式にはしない。
- 表示範囲外の結果や未取得ページまで先回りして解決しない。スクロール中の短い表示だけで取得を乱発しないよう、可視範囲が落ち着いてから処理する。
- 同じ曲の検索・再生・保存からの同時要求は一つにまとめる。曲の選択後は優先度を上げる。
- 成功したが追加情報なしという結果を記憶し、同じ画面を開くたびに取り直さない。暫定案は30分の再確認間隔。通信失敗は別扱いとし、回復時や明示的な再確認操作を再試行の契機にする。
- 取得結果のキャッシュは曲IDだけでなく取得元・表示言語・認証条件も区別し、ある条件の「情報なし」を別の条件へ無条件に流用しない。
- 同時取得数や可視範囲判定の待ち時間は、実装時に小さい値から計測して決める。通信完了まで初回表示を止める方式にはしない。

## 6. 後から届く情報の採用規則

| 得られた情報 | 採用する更新 | しないこと |
| --- | --- | --- |
| 曲の個別アーティストとしてA・Bの二項目を採用済みで、AのオンラインIDだけ対応を確認できた | Aの項目にAのオンラインIDを保存する。Bの項目は名前・内部ID・曲との関連を保持し、オンラインIDは未確認のままにする。BだけのオンラインIDを確認できた場合は、Bの項目だけに保存する | オンラインID未確認の項目を表示・登録から消さない。二項目の名前を、一項目のオンラインページ名だけで置き換えない |
| 結合表示に対し一つのオンラインページだけ判明 | 独立したページ候補を保持 | 結合名全体をそのページ名へ置換しない |
| 同一曲の個別一覧A・Bを採用できた | 元表示を残して個別一覧を設定し、全画面へ反映 | 元の結合名を第三の人物として残さない |
| より薄い検索結果・通信失敗が後から到着 | 確認済みの表示・人物関係を維持 | 到着順だけで確かな情報を巻き戻さない |
| 同じIDに別言語の名前が付く | IDの対応と曲の表示名を別に保持 | 表記不一致だけで別人物を作らない |
| 別の確かな取得元と人数・IDが衝突 | 元表示と既存の採用結果を保ち、調査対象として記録 | 単純な和集合で人物を増やしたり、一方で全置換したりしない |

対象曲ID、取得元、取得条件、採用根拠を照合する。アルバムの見出しだけで曲の個別一覧を置き換えない。
名前・関係の変更は関連一式を整合させて反映し、いいね・登録日時・ダウンロード・再生位置を保持する。
検索結果の順序・スクロール位置を変えず、曲Aの後着結果を現在再生中の曲Bへ適用しない。

## 7. 名前一覧の採用と、まだ決める必要がある境界

以下を、表示とID補完の仕様とは別に明示する。

- 曲のアーティスト欄に個別名が構造として並ぶ場合は、オンラインIDがなくても個別表示の材料として採用する。混在するリンクなしの名前も落とさない。
- 一つの名前RunにIDがある通常例は、その名前全体を保持する。記号を含むことだけで分離対象にしない。
- クレジットを補助情報として使う場合は、まず対象曲IDと役割を確認し、個別の名前Runから候補を得る。結合表示の文字列を区切り文字で切って候補を作らない。
- 曲の元表示を、独立して取得した候補名で不足・余りなく説明できるかは整合確認に使える。ただし、文字列を再構成できることだけで人物や役割が確定するわけではない。
- 今回の対象曲は、元表示に両名があり、演奏欄に両名が独立してあるため、両者を曲のArtistとして採用する案を推奨する。ただし一般化するクレジット採用条件は、追加の実例も含めて合意が必要。
- この補完案を一般化する場合の最低条件候補は「対象曲ID一致」「名前はクレジットの独立項目から取得」「元表示を余りなく再現」「候補の対応が一意」「確認済みの単独名・IDと矛盾しない」。これも推論を含むため、明示的な個別Artist欄からの取得と同じ確度とは扱わず、採用根拠を残す。
- 「演奏欄全員を無条件に採用」「作詞・作曲や提供者も混ぜる」「結合名を既知名で部分一致分割する」は採用しない。

同名・外部IDなしの人物を別アルバム間で自動統合する条件も未確定。根拠がない一致は同一人物として確定せず、曲ごとの関係と取得元を保持する案とする。
これらの境界が未確定でも、IDなしの個別名を表示し、内部ページを利用可能にし、後着のIDだけを追加する設計は共通に使える。

## 9. 合格条件案

1. 初回検索でA・Bの個別名がありIDがなくても、両名を表示できる。後からIDが来ても名前は消えない。
2. 元表示だけでIDなしの対象曲を、検索後に補完できる。再検索せず行と人物候補が更新される。
3. 補完完了前に再生・保存しても、後から検索行・プレイヤー・曲一覧・キュー・通知・DBの採用結果が揃う。
4. AだけのIDが後着してもBを失わず、未分離の結合名を第三のArtistとして残さない。
5. IDなし人物を未保存曲から開ける。ページを開くために曲をライブラリへ勝手に登録しない。選択元の曲の追加欄は表示せず、閲覧したオンライン曲を内部ページのシャッフル対象に混ぜない。
6. 通信失敗・オフライン・再起動・古い応答の後着で、確認済みの名前・関連・ユーザー操作状態が退行しない。
7. Earth, Wind & Fireを分割せず、通常のデュエットは二項目のまま保持する。アルバム見出しが一名でも曲の二名を失わない。
8. 画像取得によるページ名更新で曲の表示名が勝手に変わらず、同じ要求を画面ごとに重複実行しない。

これらは今後の検証条件であり、現時点でPASSを付けない。今回の作業は仕様案の文書化のみ。

## 10. 初回オンラインIDなしのケース表（2026-09-07の提案）

### 10.1 表の前提と、DBへ保存するタイミング

「アーティストが1名分送られてくる」は、この表では「アーティスト名を示す表示項目が一つ送られてくる」と解釈する。
その一項目が一個人・一グループの正式な名前なのか、複数アーティストの結合表示なのかは、別途調べる。
「オンラインIDを後から取得できた」は、IDの文字列を入手しただけでなく、そのIDがどの個別アーティストのページを指すか確認できた状態とする。
「未確認」は、調査しても対応するIDが得られない場合を含む。ページの不存在は断定しない。

表の「DB登録」は、曲情報をDBへ保存するタイミングで、アーティスト情報と曲との関連を何件・どの名前で保存するかを示す。
同一アーティストと確認できる既存項目があれば再利用するため、記載した件数がすべてDB全体の新規追加件数になるとは限らない。
オンラインID未確認でも、個別名を採用した項目には内部IDを持たせる。オンラインIDの確認後も内部IDと既存の曲との関連を維持する。
名前が一致するという理由だけで、別の曲・アルバムのIDなし項目と同一人物に統合しない。

| 操作・状態 | DB登録との関係 | ライブラリへの追加との関係 |
| --- | --- | --- |
| 検索結果を表示しただけ | 表示と追加解析に共通状態・結果キャッシュを使う。検索に出た全件を個別Artistとして登録する提案ではない | 検索に出ただけではライブラリへ追加しない |
| 再生・キュー保存などで曲情報を保存する | 下表の確認済み個別名を、曲との関連とともに保存する | DBに保存したことだけでライブラリ追加済みとはしない |
| オンラインアルバムを開いて曲情報を保存する | 現行コードにも閲覧時のDB保存がある。改修後は下表の採用規則をその保存にも適用する | アルバムを開いたことだけでライブラリ追加済みとはしない |
| ライブラリ追加・ダウンロードなどで曲情報を保存する | 下表の確認済み個別名を、曲との関連とともに保存する | ライブラリやダウンロードの掲載条件に従う |

現行の閲覧時保存の根拠は [AlbumViewModel.kt](../app/src/main/java/com/dd3boh/outertune/viewmodels/AlbumViewModel.kt) と
[DatabaseDao.kt](../app/src/main/java/com/dd3boh/outertune/db/DatabaseDao.kt)。
DBにArtistが存在することと、ライブラリのアーティスト一覧に掲載されることを同義にしない。

### 10.3 一部だけ確認できた場合に、追加で必要な保存と操作

第10.2節の「一部だけ確認できた個別名をArtistとして登録する」は、今回具体化した提案である。
この場合、Artistテーブルにある名前だけを連結して各画面に表示すると、未確認の部分が消えてしまう。
そのため、曲には元の文字列 `Alpha & Beta` と「個別一覧全体は未確定」という状態を保存する。
確認済みのArtist `Alpha` と曲との関連を保存すると同時に、四画面の曲名下には `Alpha & Beta` を表示する。

| 名前の確認結果 | 個別アーティストを選択する操作 |
| --- | --- |
| 全体が一つの名前 `Alpha & Beta` と確認できた | `Alpha & Beta` という一アーティストを選択できる。オンラインID未確認なら内部ページ、対応確認後はオンラインページも利用できる |
| `Alpha` だけ確認でき、残りは未確認 | 曲の「アーティスト情報」から確認済みの `Alpha` を選択できる。曲名下の元の文字列全体をAlphaのページへのリンクにはしない。未確認部分を個別アーティストとして選択する操作は作らない |
| `Alpha` と `Beta` の全個別名を確認できた | `Alpha` と `Beta` を別々に選択できる。各項目は内部ページを持ち、オンラインIDの対応を確認できた項目ではオンラインページも利用できる |

まだ一つも個別名を確認できない場合は、元の文字列を表示用の曲情報として保持し、推測した個別Artistは登録しない。
この状態は「全体が一アーティストと確認済み」とは区別する。
未確認部分に関係しそうなページIDが得られても、個別名と曲への関係を確認するまでは候補情報として保持する。
例えばBetaの個別名と対象曲への関係を確認でき、未確認の残りがなくなった場合は、第10.2節の「全個別名を確認」の行へ移る。
残りに未確認の名前がある場合は、確認できた個別項目を増やしつつ、一覧全体は未確定のままにする。
同じオンラインIDが複数の個別名に対応するように見えるなどの競合は、第6節に従って記録し、推測で統合・付け替えを行わない。

### 10.4 アルバム全体のアーティスト名は、曲ごとのアーティスト名と区別する

第10.2節のアルバム列は、アルバム画面内の対象曲の行にあるアーティスト名を指す。
現行の通常オンラインアルバム画面にもこの表示があり、[AlbumScreen.kt](../app/src/main/java/com/dd3boh/outertune/ui/screens/AlbumScreen.kt) から
[SongItems.kt](../app/src/main/java/com/dd3boh/outertune/ui/component/items/SongItems.kt) の曲行を使っている。

| アルバムに関する表示・保存箇所 | 提案する扱い |
| --- | --- |
| アルバム画面内の対象曲のアーティスト名 | 第10.2節の各行に記載した文字列を表示する。同じ曲の検索・プレイヤー・曲一覧と情報を共有する |
| アルバム画面上部の、アルバム全体のアーティスト名 | アルバム自身の情報を使う。一曲の個別名を解析しただけでは置き換えない |
| アルバム一覧で、アルバム名の下に表示するアーティスト名 | アルバム自身の情報を使う。一曲の個別名を解析しただけでは置き換えない |
| DBのアーティストとアルバムの関連 | アルバムのアーティストとして採用した根拠で登録する。曲のArtistとして登録したことだけでは、Album Artistとしても登録しない |
| アーティスト内部ページの関連アルバム | 曲に参加した根拠と、アルバムのアーティストである根拠を分ける。曲への参加だけを理由に、アルバム見出しへその名前を追加しない |

例として、アルバム自身のアーティスト名が `Gamma` と確認できている場合、対象曲の解析結果が第10.2節のどの行であっても、アルバム見出しとアルバム一覧のアーティスト名部分は `Gamma` と表示する。
アルバム自身の元表示が `Alpha & Beta` で未分離なら、曲の個別名が二項目に分かれても、アルバム見出しの根拠を確認するまでは `Alpha & Beta` と表示する。
アルバム自身についても二項目 `Alpha`・`Beta` を採用できた場合に、アルバム見出しとアルバム一覧を `Alpha、Beta` へ更新する。
アーティストのオンラインIDを共有できることと、そのアーティストをどの曲・アルバムに関連付けるかは別に判断する。

### 10.5 初回から二つの個別名があり、両方のオンラインIDがない場合

名前とオンラインIDは別の情報なので、この状態をアプリで表現することは可能である。
ただし、以下の実観測と、コード上受容できることを区別する。

### 10.6 取得途中・失敗・後着更新

オンラインIDの未確認は、未取得・取得中・通信失敗・取得成功だが対応なし・候補の対応が曖昧という状態を内部で分ける。
いずれも、既に採用した個別名を画面から削除する理由にはしない。
検索結果を表示している間、再生開始後、DB保存後のどの時点で個別名やオンラインIDを確認しても、対象曲の共通状態を更新する。
再検索や曲の再登録を要求せず、表に記載した対象曲の四画面と保存情報へ反映する。

## 11. 検索結果の三点メニューに情報が必ず表示されるか

2026-09-07の確認。メニュー項目があること、実際の名前が表示されること、個別候補を選べること、ページへ移動できること、ページ内容の取得に成功することを分ける。

### 現行コードの表示条件

[YouTubeSongMenu.kt](../app/src/main/java/com/dd3boh/outertune/ui/menu/YouTubeSongMenu.kt) は、次の条件を使う。

- メニュー上部の曲情報には、検索の曲データにあるアーティスト名をオンラインIDの有無にかかわらず連結して表示する。アルバム名はこの上部情報に含まれない。
- アーティストページへ移動するメニュー項目は、検索の曲データにIDがnullではないArtistが一件以上ある場合だけ表示する。名前があっても全項目のIDがnullなら、この移動項目は表示しない。
- アルバムページへ移動するメニュー項目は、検索の曲データにalbumがある場合だけ表示する。
- 名前だけのArtistがありalbumがない場合は、上部に名前が表示されても、アーティストとアルバムの移動項目は両方とも表示しない。
- 取得したアーティスト候補は引数をキーにしないrememberで保持している。後着更新は、検索の行だけでなく、開いている三点メニューとその候補一覧にも反映する変更が必要。

これはコード上の条件を確認した結果であり、今回エミュレータで操作した結果ではない。

### 仕様案で保証する範囲と、保証できない情報

第10.2節の三つの解析結果では、いずれも元の表記や採用済みの個別名がある。
そのため、オンラインIDが未確認であることだけを理由に、アーティスト名やアーティスト情報を確認する入口を消さない仕様にする。

| 解析結果 | 三点メニューから確認できるアーティスト情報 |
| --- | --- |
| 名前全体が一つのアーティスト名と確認済み | 名前全体と、そのアーティストの内部ページ。オンラインIDの対応を確認できた場合はオンラインページも利用できる |
| 一部の個別名だけ確認済み | 元の表記全体、確認した個別名、その個別名の内部ページ。未確認部分の個別名やページは作らない |
| 全個別名を確認済み | 全個別名と、それぞれの内部ページ。オンラインIDの対応を確認できた項目ではオンラインページも利用できる |
| 個別名は未確認だが元の表記がある | 元の表記と、取得できたクレジット。個別アーティストの選択は保証しない |
| 元の表記も個別名もない | 「アーティスト不明」と確認状況。実際の名前を表示することは保証しない |

アルバムの情報は、アーティスト名の解析とは独立して確認する。

| 取得できたアルバム情報 | 表示・操作として可能な範囲 |
| --- | --- |
| アルバム名と、そのアルバムへの対応を確認したID | 名前の表示とページへの移動を用意できる。移動後の通信成功までは保証しない |
| アルバム名だけ | 名前を表示できる。確認済みのオンラインアルバムページへの移動は保証しない |
| 対象曲との対応を確認したアルバムIDだけ | そのIDを使った取得・移動は可能。取得前や通信失敗時に実際のアルバム名が表示できるとは限らない |
| アルバム名もIDもない | 実際のアルバム名や移動先を表示できない。アーティスト名を分離できたことでは補えない |

追加のUI案として、三点メニューに情報確認の入口を常設し、情報がない場合は「アルバム情報を確認できません」などを示すことは可能。
入口の常設と、実際の名前やページ内容を必ず取得できる保証は別である。アルバム情報の入口を常設する具体的なUIは、これまでの案では未確定。
