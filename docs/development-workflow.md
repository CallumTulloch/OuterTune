# 効率的な開発手順

2026-09-05。アーティスト改修の巻き戻しに合わせ、調査の重複と検証のやり直しを減らすための方針。
アーティストの完成仕様はまだ決めていない。次はユーザーと課題を整理する。

## 1. 課題を短く定義する

課題ごとに `docs/verification/records/YYYY-MM-DD-<課題>.md` を一つ作り、次を先に書く。

- 現象：どの曲・画面・操作で何が起きるか。
- 期待する動作：ユーザーが何をできればよいか。
- 根拠：確認済みの応答・ID・DB状態と、未確認の仮説。
- 今回の範囲と合格条件：目で確認できる結果を少数に絞る。

この記録を調査・実装・検証で更新し、同じ内容を複数の台帳へ転記しない。
通常の実装判断は既存の依頼条件から進める。ユーザー体験を変える未確定仕様は課題整理で確認する。
調査だけの依頼では、調査を超えて実装やビルドを始めない。

## 2. 一度に一課題を解決する

- アーティスト、検索構成、再生アニメーションなどを同時に変更しない。
- 再現例と影響する経路を確認してから、必要な範囲だけ編集する。
- 以前の応答fixture・調査記録は保全先から必要なものだけ参照する。旧テストの期待値を新仕様の根拠にしない。
- 外部データの解釈は、表示名・識別子・役割・内部登録の違いを明示する。「ローカル」だけで意味を済ませない。
- オンライン情報が欠ける場合と通信に失敗する場合を区別し、確認済みの関係を推測で上書きしない。

## 3. 検証の費用を変更に合わせる

| 段階・変更 | 行う確認 |
| --- | --- |
| 文書・調査のみ | 差分、参照先、記録の整合。Gradleは不要 |
| 軽微な見た目・文言 | 影響画面の確認。実装をなぞるだけの単体テストは増やさない |
| パーサー・DB・非同期処理の編集中 | 実際の不具合や重要な境界条件を捉える近傍テスト |
| ソース確定後 | 変更モジュールの関連テストを一度実行。失敗や追加修正があれば必要な範囲を再実行 |
| 配布依頼時 | 関連テスト後、core-release / arm64-v8aを生成して成果物を確認 |

同じ作業ディレクトリでGradleを並列実行しない。全variant、全lint、全テストやclean buildは、変更範囲・失敗原因から必要な理由がある場合に限る。
コンパイル・コード生成を含む経過時間と、テスト本体の時間を分ける。成功した確認を理由なく繰り返さない。

### コンパイル・debug・releaseの使い分け

2026-09-05のユーザー条件：必要な確認は何度でも実行してよい。回数制限ではなく、目的のない再実行を避ける。今回作るAPKはarm64のみ。

- コンパイルはビルドの一工程。対象テストやAPK生成に必要なコンパイルはGradleが実行するため、毎回「コンパイルのみ → テスト → debug APK → release APK」を全段実行しない。
- 型や構文だけを早く確認したい場合は対象のコンパイル、ロジックを確かめたい場合は近傍の単体テストを選ぶ。単体テストだけならインストール用APKは不要。
- 画面・DB・再生などを調べる途中で、デバッガや繰り返しの端末確認が必要な場合だけ `coreDebug` のAPKを作る。単体テストで `coreDebug` を使うことと、debug APKを作ることは別。
- 最終確認・配布は `coreRelease` / `arm64-v8a`。releaseにはコード・リソース縮小処理があるため、debugで確認していても実際に渡すrelease APKで主要経路を確認する。
- debug APKを経由する必然性がなければ、関連テスト後に直接release APKを作ってよい。`full`、`userdebug`、universal、他ABIのAPKは今回の通常手順に含めない。
- 原因調査、修正後の確認、最終成果物の更新に必要なら何度でも再実行する。実行前に目的と対象を短く伝え、成功後は同じ入力に対して根拠なく繰り返さない。
- 通常はビルド出力を残してGradleの差分判定を使う。`clean`、`--rerun-tasks`、キャッシュ削除は破損などの具体的な理由がある場合だけ行う。ブランチの切替だけを理由にcleanしない。
- arm64対応端末でAPKを確認する。他ABIのエミュレータしか使えない場合は実行確認の制約として伝え、他ABIのAPKを自動的に追加しない。

**2026-09-07の設定対応**：`app/build.gradle.kts` のAPK分割は `arm64-v8a` のみ、universal生成は無効。
TagLibのネイティブビルドもルートの設定でarm64のみに限定した。submodule本体は変更していない。
以前の他ABIのAPKがbuild出力に残っていても今回の成果物と混同せず、最新の出力情報と生成日時を確認する。

参考：[Androidのビルド種別とAPK生成](https://developer.android.com/build/building-cmdline)、
[ABI別APKの設定](https://developer.android.com/build/configure-apk-splits)、
[Gradleの差分ビルド](https://docs.gradle.org/current/userguide/incremental_build.html)。

アーティストの登録・遷移を直す場合は、単体テストだけで完了にしない。
新規データで対象曲を再生 → ライブラリ登録 → 人物と曲のDB関連 → プレイヤーとライブラリからの移動 → 画像 → 再起動後の維持、を一連の合格条件にする。
通信失敗時に既存情報が壊れないことも確認する。人物の扱いなど具体的な期待値は[アーティスト表示仕様](artist-display-spec-draft.md)を参照する。

### エミュレータの操作担当を明示する

2026-09-05のユーザー条件：エージェントによる操作が遅い場合は簡単な操作をユーザーへ依頼してよい。
ユーザーが自由に利用できるか判断できるよう、操作担当と状態維持が必要な時間をチャットに表示する。

- 利用前に対象エミュレータ、目的、操作担当を短く伝える。エージェントが操作する場合は「こちらで操作します。完了の連絡まで、このエミュレータの操作をお控えください」と明示する。
- 画面操作に限らず、インストール、アプリ再起動、データ初期化、自動操作など、ユーザーの操作と干渉する処理も事前の案内に含める。
- 起動、検索、数回のタップ、見た目の確認などは、ユーザーに依頼したほうが速ければ任せる。目的、短い番号付き手順、期待結果、報告してほしい点をまとめて提示し、操作を一手ずつ細切れに依頼しない。
- ユーザーへ引き渡した後は、完了の返答が来るまでエミュレータの画面・アプリ・データ状態を変更しない。返答待ちの間はコード調査や資料整理など、干渉しない作業を進める。時間経過だけで操作を再開しない。
- 再現条件の維持や繰り返し操作が重要ならエージェントが担当する。操作が遅い、または同じ試行を繰り返して進まない場合は、ユーザーへの操作依頼などに切り替える。
- 状態維持が必要なら、対象と理由を伝える。例：「再起動前のDBを確認しています。このアプリは終了・操作せず、そのままお待ちください」。ビルドやコード編集だけでエミュレータを利用しない間は、必要なく操作を制限しない。
- 完了・中止・引き渡し時には「こちらの操作は終了しました。自由に操作して大丈夫です」と明示する。ユーザーに操作を控えてもらったまま、別作業へ移ったりターンを終了したりしない。状態維持が引き続き必要な場合は、その理由と解除条件を伝える。
- ユーザーから使用したい旨の連絡があれば、干渉する処理を区切り、引き渡しを明示する。利用前の案内は担当の共有であり、既に許可された通常のテスト操作に毎回の承認手続きを追加するものではない。
- 検証記録では、エージェントが直接確認した結果とユーザーから報告された結果を区別し、使用APKと確認内容を残す。

## 4. 結果を短く正確に残す

記録には対象ソース（commitと未コミット差分の有無）、実行コマンドまたは操作、結果・件数・概算時間を残す。
APKを配布する場合はvariant・ABI・SHA-256も記載する。APKや長大なログはコミットしない。

- `PASS`：記録した最終ソース・成果物で実行して合格。
- `OBSERVED`：途中版でのみ確認。最終版は未確認。
- `FAIL` / `SKIPPED`：失敗とテスト側のスキップを区別する。
- `BLOCKED`：端末や認証などがなく実行不能。必要な条件を書く。
- `DEFERRED`：意図的な後回し。同じ記録に安定したID・再現手順・合格条件・実行時期を書く。

中心となる合格条件が未確認なら完了扱いにしない。自動テスト成功とアプリ上の問題解決を区別する。
コード、DB、動作仕様の変更はこの記録と合わせて一つの改修としてまとめ、コミット本文に可能なら `Verification: <記録のパス>` を付ける。
DB変更ではバージョン・schema JSON・移行または初期化方針を揃える。今回のユーザー条件は既存データ削除可・移行不要だが、データ削除をコード変更とは別に扱う。

## 5. 作業の区切り

完了時は「変更点・確認結果・残る課題」を短く報告する。
中断時は同じ記録へ現在のブランチ、未コミット変更、次に行う一手を追記する。
次回はこの記録から再開し、解決済み事項やビルド環境を最初から調査し直さない。
